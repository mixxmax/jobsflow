# JobsFlow（求职全流程）

[繁體中文](README.md) · [简体中文](README_ZH-CN.md) · [English](README_EN.md)

### 找得准 · 写得像 · 投得稳

把岗位检索、公司研究、JD 分析、定制简历、Cover Letter 和投递确认连成一条线。

JobsFlow 不是“帮你写一份简历”的工具，而是一个**帮你搜岗位，做材料，整理投递信息**的本地优先求职执行系统。

## 🆕 最新更新 · 2026-08-15

- **从“模型自觉遵守”升级为代码约束的工作流**：统一网关、政策规则、状态机、任务包和事后门禁接通 `/scan → /push → /materials → /apply`；扫描只展示 lane/评分，不入表、不分配永久编号；`/push` 必须预览后经用户确认，归档必须预览确认，`/apply` 永不自动提交。
- **召回、评分和成本分开控制**：URL 级 JD 缓存优先复用，摘要缺失/过短和灰区岗位会被救援；深取受节能/平衡/广覆盖预算控制，完整 JD 决定深评，未取到全文的岗位保留为 `待审-JD不足`，不会静默丢失。
- **CV/CL 先审内容，再制作文件**：主模型先保存结构化 canonical CV/CL；系统随后自动派发一个独立上下文的子 Agent，只读缓存 JD、完整 CV/CL 和精简审计规则，集中核查 JD 回应、STAR、LLMO 证据位置、跨材料一致性、残句及模板残留。子 Agent 不审 Email、DOCX/PDF 或版式，也不直接改材料；同一模型可在独立上下文中承担审计，流程不绑定特定模型供应商。
- **返修有边界，输出不走捷径**：子 Agent 只返回带段落定位的 findings，主模型只修改命中的内容块，再交回独立审计；每岗最多三审，同一问题重复出现会熔断并转人工检查。内容通过后，系统才从对应 lane 的基础 DOCX 统一渲染并转 PDF，页数、文字层、文件名和元数据由确定性检查负责。
- **本地优先的台账同步**：本地 ledger 是岗位事实源，本地 CSV 是可直接使用的表格；Google Sheets 只是可选投影。同步失败可重放，远端变化先 reconcile，用户字段只能通过明确的 `sync pull` 导入。
- **入表展示有固定协议**：用户确认入表后，新批次固定插在表头下方、标记“本轮新增”并以米色高亮；旧批次自动降为“较早入表”。这是代码级规则，不由模型自行选择顺序或样式。
- **更适合能力相对有限的模型**：模型只处理受限的语义判断和表达，薪资、语言、资格、状态转换、证据绑定和高影响副作用由确定性规则兜底。

## 🎯 解决什么问题？

求职难，往往不是「找不到链接」，而是**整条链路运营不起来**：

| 痛点 | 常见问题 | JobsFlow 怎么做 |
|------|----------|-----------------|
| 岗位太多 | 浏览器标签、聊天记录堆成山 | 只在你设定的**目标与地点范围**里搜 |
| 不知道先投谁 | 凭感觉乱投 | **两段评分 + 六维打分**，优先级看得见 |
| 每个岗位都像重做一次 | 反复改简历、求职信，格式也不统一 | **按职业方向先做基础版**，再针对具体 JD **出一整套** |
| 进度记不住 | 「这个投了没？」 | **结构化台账**（分级、今日新到、状态、已投递变色） |
| 错过新岗位 | 想起来才搜一次 | **临时模式：只扫上次之后的新岗**，不重复不遗漏 |
| JD 重复抓取 | 评分时拉了一遍，做材料又拉一遍 | **JD 缓存**：评分时抓的全文按 URL 存下来，材料制作直接复用 |

### 为什么不是普通的 AI 求职工具？

| 普通工具 | JobsFlow |
|----------|----------|
| 看到 JD 就直接生成材料 | 先检查薪资、语言、工作权、资格和附件要求 |
| 只改关键词 | 研究公司性质、主营业务和岗位上下文 |
| 一份简历套所有职位 | 先做职业方向基础版，再做单岗位差异化定制 |
| 模型没看懂就静默跳过 | Schema、评分门槛、证据映射和覆盖度检查强制执行 |
| 默认某个行业模板 | 根据你的简历、意向和行业动态生成，不把法律/合规当默认 |
| 自动替你提交 | 你审核材料，最后一步始终由你确认 |

**一句话：** 少内耗，多完成投递。

### 你会得到什么？

- **少投错，也少漏掉**：初评按信息质量调度，完整 JD 决定最终分数；信息不足的岗位会明确待审。
- **写得更像这个岗位**：结合公司性质、主营业务、岗位上下文和 JD 重点，分别定制简历与求职信。
- **模型不聪明也不容易漏**：薪资、语言、工作权、资格等硬要求由确定性 preflight 和质量门槛兜底。
- **始终由你做决定**：系统准备材料和确认清单，但不会替你自动提交申请。

## 🚀 快速开始

### 1. Clone

```bash
git clone https://github.com/mixxmax/jobsflow.git
cd jobsflow
```

### 2. 安装

```bash
PYTHON_BIN="$(command -v python3.12 || command -v python3.11 || command -v python3)"
"$PYTHON_BIN" -c 'import sys; assert sys.version_info >= (3, 10), "JobsFlow requires Python 3.10+"'
"$PYTHON_BIN" -m venv .venv
source .venv/bin/activate
python3 -m pip install --require-hashes -r requirements.lock
python3 setup.py --doctor
```

跟你的 AI 助手说：

```
/setup ~/Documents/my-cv
```

系统会：读简历 → 问你想找什么类型的工作 → 询问扫描深度（节能/平衡/广覆盖）和保留偏好（宽松/标准/精选）→ 生成配置（搜索关键词、追踪表头、方向字母）。然后问：

```
你想先做什么？
先做基础版简历（按方向分 A-F 版本，可选 G 能力扩展）
还是先开始检索新职位？
```

- 选 **先做基础版** → 系统引导你按方向建立 A-F 基础简历版本（需要时可启用 G 能力扩展）
- 选 **先检索** → 直接扫新职位

> 没有 AI 助手？终端运行 `python3 setup.py --resume-folder ~/Documents/my-cv` 也可以。

### 3. 开始用

```
/scan              # 扫新职位
/push              # 先预览；用户确认 proposal 后才写入（可用 --local-only）
/materials 编号      # 给某个岗位做材料（编号从追踪表中来）
/apply 编号           # 检查材料并进入投递确认（不会自动提交）
```

### 我们的 LLMO 策略

JobsFlow 不靠关键词堆砌，而是把 **JD 要求 → 已核实证据 → CV / Cover Letter / 申请邮件** 连成一条可追溯链路：先判断哪些要求有真实证据，再把最相关的证据放到模型和 ATS 最容易读取的位置。这样做的目标是让真实能力被正确理解，不是伪造经历、操纵 ATS 或承诺固定加分。

在深度 JD 评分中，简历匹配还可以进入 **Agent-in-the-loop 语义匹配**：系统把“事实基线”和“能力上沿”分开提交给当前执行任务的 agent，由 agent 判断画像与 JD 核心职责的语义关系。`/setup` 会询问画像上沿幅度：低（保守）、中（平衡）或高（扩展）；这个选择只调节可迁移能力的判断范围和分数上限，任何档位都不能把潜力写成已做过的经历。语义任务未完成时，扫描预览会明确标记 `pending_fallback`、记录待处理数，并将关键词回退限制在 4.0 以内；正式 `/push` 默认不会把这类行写入台账，需完成任务并重评后再推送。

### 三处大模型介入，其他环节保持确定性

用户画像不是机械的“简历关键词 = 岗位关键词”死对比，而是由简历事实、求职意向、行业常见要求和用户选择的上沿幅度共同形成。画像生成后需要用户确认；画像不会随着某一个职位偷偷改变。

```text
低频：/setup 或 /intent confirm
  简历事实 + 求职意向 + 行业快查
              │
              ▼
      [LLM ① 生成画像] ──→ 用户确认 ──→ facts_anchor / capability_upper
                                                   │
每次深评：扫描后先查 URL 缓存（命中 = 0 网络请求）   │
  未命中 → LinkedIn CLI → JobsDB 浏览器兜底 → CT 不开浏览器 → teaser 兜底
              │                         │
              └────────── 已缓存 JD ──────┘
                         │
             ┌───────────┴───────────┐
             ▼                       ▼
 [LLM ② 职位定性]              [LLM ③ 简历匹配]
 公司性质 + 职位类型            direct / transferable /
 lane + company_brief           upper_only / none + 分数
             └───────────┬───────────┘
                         ▼
             确定性封顶、资格检查、lane/层级预览
                                      │
                         用户查看后明确确认入表
                                      │
                         分配永久编号并写入台账
```

三处介入中，②和③都只消费扫描阶段抓到的缓存 JD，不重新打开门户；能力相对有限的模型也可以按 `list → show → complete` 的结构化任务逐项执行，遗漏或未完成时自动回退到规则结果。公司简介会在有 agent 结论时写入「公司简介」列，否则明确标记为待核实。

### 节能设置

- URL-keyed JD 缓存默认保留 60 天，缓存文件保存全文、来源、字符数和抓取时间；评分、材料制作和重评优先复用缓存。
- 初评 3.3 是内部直接调度线，不是用户的最终取舍线；摘要缺失/过短、已有缓存或落在灰区的岗位会被救援。
- 扫描深度把未命中缓存的网络深取控制在节能约 10、平衡约 20、广覆盖约 40 个；缓存读取不占预算。没拿到完整 JD 的岗位会进入 `待审-JD不足`，`/scan temp` 仍只扫上次之后的新岗。
- 最终保留偏好由用户选择宽松 3.0、标准 3.3 或精选 3.5；它只重新筛选已保存的深评分数，不触发新的网络抓取。
- LinkedIn 优先使用 CLI detail；JobsDB 才使用 Playwright 兜底；CTgoodjobs 默认不打开浏览器。需要时可设置 `PORTAL_JD_BROWSER=0` 完全关闭浏览器深取。
- PDF 继续使用内容哈希缓存；未改变的 DOCX 不重复转换。

## 📁 文件夹 + 台账：一套可迁移的求职资料系统

JobsFlow 不把所有东西塞进表格或聊天记录，而是用两层结构管理求职：**文件夹管理材料和证据，CSV/Google Sheets 管理岗位和状态**。

```text
JobSearch_2026/
├── 00_Profile/                    # 简历事实、求职意向、搜索配置
├── 01_Masters/                   # 按方向保存基础 CV / Cover Letter（A-F；可选 G 能力扩展）
│   └── <方向>/<层级>/<岗位编号_公司>/
│       ├── jd_full.md             # 完整 JD
│       ├── company_research.md    # 公司性质、主营业务、来源
│       ├── application_preflight.json
│       ├── tailor_plan.md         # JD → 候选人证据映射
│       ├── job_manifest.json      # 生成字段、人工覆盖和输入指纹（私有）
│       ├── materials_validation.md # 投递前统一验证报告
│       └── CV / Cover Letter / PDF
├── 02_Tracker/                   # CSV 台账、JD 缓存、扫描结果
└── 03_Applications/              # 可选的最终投递归档
```

| 内容 | 文件夹 | CSV / Google Sheets |
|------|:------:|:------------------:|
| JD、公司研究、证据映射 | ✓ | — |
| CV、Cover Letter、PDF | ✓ | — |
| 匹配分、优先级、投递状态 | — | ✓ |
| 材料版本与修改记录 | ✓ | 可记录链接 |

扫描预览只提供职位、lane、层级、分数、URL 和 JD 状态，不产生永久岗位编号。
只有用户确认 `/push` proposal 后，系统才分配岗位编号并把台账行写入本地 CSV
或 Google Sheets。每个已入表的岗位编号再把台账行和材料包对应起来；Google
Sheets 只是可选的台账同步，不是 CV 或 Cover Letter 的存储位置。

材料包里的 `job_manifest.json` 是这条交接链的私有契约：系统自动生成职位名、JD 关键词、文件名和依赖指纹；你确认过的措辞可以放在 `overrides` 中，批量重跑不会覆盖。JD、画像、公司研究或方向发生真实变化时，旧 CV/Cover Letter 会被标记为待重做，而不是静默沿用。完成材料后可运行 `python3 -m tools.job_materials validate --package <路径>`，统一检查猎头名称外泄、目录层级、英文材料中文残留、残缺句、公司名和求职信页数。

## 🔢 Lane、层级与入表后的岗位编号

扫描时只分配 lane（A–F，可选 G）和匹配层级；检索结果不会出现永久编号。
用户确认入表后，系统才会为该岗位生成压缩了三层信息的正式编号：

```
C0-005
││  │
││  └── 序号：该前缀下连续编号（001 起，接续已有最大号）
│└───── 层级：0=核心 / 1=一级 / 2=二级 / 3=剔除
└────── 方向：A-F（可选 G 能力扩展），由 setup 根据你的职业自动生成
```

**方向字母**（仅作结构示例；实际内容由 setup 根据简历、意向和行业生成）：

```
┌─────┬────────────────────┬──────────────────────────┐
│  A  │ 产品运营             │ product operations         │
│  B  │ 商业运营             │ business operations        │
│  C  │ 项目管理             │ program management         │
│  D  │ 数据运营             │ data operations            │
│  E  │ 客户运营             │ customer operations        │
│  F  │ 相邻机会             │ adjacent opportunities     │
│  G  │ 可选创新/科技能力线   │ optional innovation/tech   │
└─────┴────────────────────┴──────────────────────────┘
```

**层级数字**（通用，不随职业变化）：

```
┌─────┬──────┬──────────────────────────────────────┐
│  0  │ 核心  │ 高度匹配（分数 ≥ 3.5）-> 优先投递       │
│  1  │ 一级  │ 中上匹配（分数 ≥ 3.3）-> 值得认真评估    │
│  2  │ 二级  │ 中等匹配（分数 ≥ 2.5）-> 供给稀缺时考虑  │
│  3  │ 剔除  │ 不匹配 -> 不入库                        │
└─────┴──────┴──────────────────────────────────────┘
```

**示例：**

```
C0-005  =  项目管理方向 · 核心匹配 · 第 5 号
A2-012  =  产品运营方向 · 二级匹配 · 第 12 号
B1-003  =  商业运营方向 · 一级匹配 · 第 3 号
（层级 3 的预览行不会进入确认入表，也不会分配正式编号）
```

## 🌐 支持哪些求职网站？

| 来源 | 岗位检索 | 深度 JD | 说明 |
|------|:--------:|:-------:|------|
| LinkedIn | ✓ | ✓ | 优先使用深度 JD；已抓取内容可由材料流程复用 |
| JobsDB | ✓ | 部分 | 结构化信息可直接使用；定制材料建议粘贴 JD 全文 |
| CTgoodjobs | ✓ | 部分 | 结构化信息可直接使用；定制材料建议粘贴 JD 全文；用户可以自行接入 capsolver 等解决方案 |
| FreeHire | ✓ | 手动 | 作为额外岗位来源；可按岗位标识查询详情 |

浏览器自动化是结构化接口和缓存之后的后备路径，并且不会在扫描时自动生成材料或提交申请。
Google Sheets 是可选的投递台账同步方式；不启用时可使用本地 CSV。
LinkedIn 可按用户指定地点检索；JobsDB 与 CTgoodjobs 的当前接入面向香港市场；FreeHire 覆盖多地，但筛选能力目前更偏技术岗位。

## 💡 每一步帮你解决什么

### 1. 从你真正的简历开始

**痛点：** 各种产品逼你从零填表，明明简历里都有。  
**怎么解决：** 把已有 CV/简历放在一个文件夹里，跟你的 AI 助手说 `/setup ~/Documents/my-cv`。它会读完简历、问你「你想找什么类型的工作」、自动生成搜索配置、表头、评分权重。你全程在对话里完成。

### 意向会变，也能安全增量更新

完成 `/setup` 后，可以用 `/intent add ...` 增加方向，或用 `/intent replace ...` 替换检索范围；也可以用 `/intent scan-depth 节能|平衡|广覆盖` 修改抓取成本，用 `/intent retention 宽松|标准|精选` 修改最终清单取舍。所有修改都先生成预览，只有用户明确执行 `/intent confirm` 后才写入私有配置。保留偏好变化只重筛已有深评结果，不重新打开门户；历史台账和已生成材料不会被悄悄改写。

普通聊天中随口提到的新想法不会自动改变检索范围；不明确是“增加”还是“替换”时，助手会先复述并确认。

### 2. 不同职业方向，先做不同的「基础版」简历

**痛点：** 合规岗和产品岗共用一份「万金油」简历，怎么看都只沾一点边。  
**怎么解决：** 按**岗位类型**做多套基础版。每套从你真实经历里挑不同侧重。基础版上的表述会对照原始材料做**事实核对**，不是「AI 随口一编」。

### 3. 只在范围内找岗

**痛点：** 关键词一开，噪音岗位淹没你。  
**怎么解决：** 搜索只在你的范围内跑。支持 LinkedIn、JobsDB、CTgoodjobs 与 FreeHire。新职位成批进表，一眼能看清。

### 4. 两段评分：先调度，再用完整 JD 定案

**痛点：** 一个说不清的「匹配分」，你不敢信。  
**怎么解决：** 分两关--

| 关卡 | 做什么 | 不做什么 |
|------|--------|----------|
| **初评** | 用标题+摘要确定深读优先级；内部 3.3 直接进入 | 不把标题分数当最终结论，也不要求用户调技术 gate |
| **救援** | 摘要缺失/过短、已有缓存或灰区岗位继续进入 | 不因门户卡片信息少而静默淘汰 |
| **扫描深度** | 节能约 10 / 平衡约 20 / 广覆盖约 40 个网络深取 | 缓存命中不占预算；成本不由最终分数线控制 |
| **深评** | 先读 URL 缓存，再在预算内拉完整 JD 并保存分数 | 不因用户改变保留偏好而重新抓取 |
| **入表/待审** | 用户选择宽松 3.0 / 标准 3.3 / 精选 3.5；未取到 JD 标记 `待审-JD不足` | 不把 provisional 当最终排名，也不自动做材料 |

每次扫描会分别展示初评分布和完整 JD 深评分布（`<3.0`、`3.0–3.3`、
`3.3–3.5`、`3.5+`），并报告缓存命中、网络深取、预算未覆盖和待审数量。
用户因此可以先看本轮分布，再决定维持标准线还是切换宽松/精选；系统不会
悄悄把阈值包装成客观的“岗位质量”。

六维评分：简历匹配 · 资格可行 · 方向 · 行业 · 工时 · 薪资。setup
会按职业和用户限制生成权重与硬性门槛；产品本身不内置某个行业的资格、
语言或年限假设。

每个被评分的岗位还会在私有工作区保存一份版本化的岗位评估记录：把初评、深评、
最终分数，以及“支持优势”和“待核对缺口”结构化保存，并记录 JD 与评分配置的哈希。
JD 或求职意向改变后，旧记录会被视为过期并重新评估；后续材料流程可以复用同一份判断，
避免不同岗位步骤重复猜测。记录位于 `JobSearch_2026/02_Tracker/job_assessments/`，
不会把候选人资料复制进公开产品文件。它不是只写不读的日志：CV bullet 排序、
Cover Letter/申请邮件的共同证据顺序，以及面试缺口准备都会读取同一份当前记录；
记录缺失或过期时会明确标记，不会悄悄重算后冒充原评估。

### 5. 像管项目一样管投递

**痛点：** Excel 没规矩，或进度只在脑子里。  
**怎么解决：** 结构清楚的工作簿：优先级分层、今日新职位米色高亮、从「新发现」到「已投递 / 面试」的状态流转。支持 Google Sheets 或本地 CSV。

### 6. 每个要投的岗，一次出齐材料

**痛点：** 半成品、格式乱、文件散落各处。  
**怎么解决：** 选定岗位后，为每一个岗位生成一整套：简历 + 求职信 + 投递说明 + 邮件草稿 + 发出前检查清单。

定制分两层：

| 层次 | 含义 |
|------|------|
| **基础版（按职业方向）** | 方向之间差别要大；要做事实核对 |
| **定制版（针对这个 JD）** | 在已核对的基础版上，突出这份 JD 最在意的点 |

定制版的做法：
- 先由确定性 preflight 抽取薪资、到岗、工作权、语言/牌照、年限和附件要求，生成必问清单
- 语言门会把 JD 中明确的工作语言与私有语言档案比较：未声明语言才会硬剔除，水平可能偏高只标记提醒，广告使用的语言不会被误当成岗位要求
- 薪资解析支持本地化数字、区间连字符以及 `k/M/B`、`千/万/亿` 等金额后缀；格式存在歧义时保持中性并提示核对，不会静默把范围误判成负数
- 先快查公司的性质、主营业务和岗位上下文，并保存来源
- 从 JD 提取职责要点、硬性要求与能力主题
- 由系统生成 JD→候选人证据映射、四段 Cover Letter 蓝图和质量门槛；能力相对有限的模型也不能跳过
- 从基础版的经历子弹中，按 JD 关键词匹配度打分排序，把最相关的提前
- 在有事实证据时用 STAR 重述；没有真实量化结果时不补造数字
- 与 JD 无关或弱关联的经历降序或删除
- **不编造新经历**——只重排和重写已有事实，不做 freestyle 发明
- 输出结果附带覆盖度分析：哪些 JD 要点命中了、哪些还需要你手动补充

Cover Letter 的岗位/行业匹配段：定制版会用一段 1–2 句的小段落替换通用版原有的
公司兴趣位置，按“岗位需求 → 候选人真实证据 → 可提供的价值”组织，并自然使用
JD 中重要且真实的词语。优先使用已核实的公司业务；如果没有可靠公司信息，就只
写 JD、岗位职能或行业语境；如果证据不足则保留通用版。该段不会增加总篇幅，仍以
通用版一页长度为上限，也不会因为省略它而阻断投递。

职位标题也会先经过确定性处理：职位页原文保存在 `role_display`；`A/B` 这类斜杠标题
拆成推荐主职位和备选职位，定制材料默认只写一个主职位，歧义时可用
`python3 -m tools.job_materials role show` 查看，并用 `role choose` 确认。`Paralegal (Corporate Funds)`
这类表示专业方向的括号会保留括号和词汇；只有地点、合同/工作方式或编号等明显元数据
括号会从对外职位名中移除。文件名只做必要的安全清理，不用短横线或逗号替换括号，
也不会把多个职位拼成一个新职位；Cover Letter 通常只在开头提及主职位一次。

### 一个定制示例

```text
JD 要求：Experience in developing, implementing and monitoring an operational program

JobsFlow 会把重点拆成：流程设计 · 落地执行 · 指标监控
→ 优先匹配候选人已有的流程创建、跨团队执行和数据跟踪经历
→ 在 Cover Letter 中结合公司业务，说明对该行业/公司的真实兴趣角度
→ 如果简历没有足够证据，明确标记缺口并询问用户，不自动编造经历或数字
```

### 发布者与真正用人公司分离

职位页显示的“公司”不一定就是最终用人方，可能是猎头、招聘机构或招聘咨询公司。
JobsFlow 会把发布者与用人公司分开核查，并将关系归类为 `employer`、`recruiter` 或
`unknown`：

- 猎头已披露客户：外发 CV / Cover Letter 只使用已核实的客户公司；
- 客户未披露：外发文件名不带猎头名称，Cover Letter 只写岗位和行业语境，不猜测公司；
- 无法确认：质量门槛会标记待核实，不把职位页显示名直接当成雇主。

材料包内部仍会保留发布者字段，方便追溯岗位来源；真正发送时使用
`tailor_plan.json` 中的 `material_filenames` 命名建议。这样即使岗位来自 Michael Page
等机构，投递出去的文件名和求职信也不会把机构误写成用人公司。

### LLMO 细节：让真实证据更容易被正确读到

JobsFlow 把 LLMO 做成可审计的材料契约，而不是“写进模型记忆”或承诺 ATS 加分：

- 每条已核对经历都有稳定的 `evidence_id`、允许表述和禁止推断；
- JD 要点分为 Tier 1/2，并明确标记 `covered`、`partial`、`uncovered` 或 `prohibited_to_claim`；
- CV、Cover Letter 和申请邮件共享同一证据图与数字，改动一条事实时能看出受影响的材料；
- 输出保持可解析的纯文本结构（单栏、标准章节、关键联系信息不放在图片/文本框/页眉页脚）；
- 主模型先保存带稳定 block ID 的 canonical CV/CL；系统自动启动精简的独立内容审计，子 Agent 只读 JD、完整 CV/CL、内部覆盖处置和编译规则，不读长手册、事实库、Email、DOCX/PDF 或版式；没有真实正面证据的要求只在内部标记为 `intentionally_omitted`，不得改写成主动暴露缺点的材料文字；P0/P1 只允许主模型修改 finding 指向的 block，内容通过后才统一生成 DOCX/PDF；每岗最多三审、同一问题第二次仍出现即熔断；
- 审计发现会沉淀为不含候选人原文的材料制作经验，下一次同类岗位可直接避开已知问题；
- 机器 QA 指标是内部工程指标，不是 ATS 官方分数或录用预测。

因此，即使使用能力相对有限的模型，系统也会先给出证据映射和禁止越界的边界，模型只需按蓝图重排和重述，不需要自行“猜懂”整份 JD。

材料格式和存放也不是模型可选项：只有确认 `/push` 才建立绑定的
`01_Masters/<lane>/<tier>/<job_id>_未投_<company>/` 包；`/materials` 只能在该包内写入。
CV/CL 内容通过固定的 `tools.workflow` 入口，从对应 lane 的基础 DOCX 模板渲染后再转 PDF；
缺少模板或绑定回执会直接阻断，不会把纯文本另存成“看似 DOCX”。CV/CL 也不会主动暴露
未声明的语言或其他缺口（例如不会写 “Cantonese is not declared in my language profile”）。

PDF 导出用 LibreOffice headless（不弹窗，不干扰你正在做的事）；简历和求职信默认输出一页，用户明确需要时可调整。

### 7. 跟住最新职位

**痛点：** 好岗位上架又下架，你还在改上周的求职信。  
**怎么解决：** **临时模式**记住上次刷新时间，下次只扫这段时间内的新岗。不用每次都扫满 24 小时，效率更高，也不遗漏。

```
/scan              # 临时模式：只扫上次之后的新岗（自动记忆）
/scan daily        # 扫最近 24 小时
/scan 3            # 扫最近 3 小时
```

## ❓ 常见问题

**它会自动替我提交申请吗？**

不会。JobsFlow 负责检索、分析、准备材料和投递前检查，最终提交始终由你确认。

**能力相对有限的模型也能用吗？**

可以。模型负责研究和措辞，硬要求抽取、评分门槛、公司来源、证据映射和质量检查由确定性代码兜底。

**什么职位都可以用吗？**

原则上可以用于各行业和职位。setup 会根据你的简历、求职意向和行业动态生成方向与表头；不同招聘网站的职位覆盖范围可能不同。

**简历会不会自动上传？**

默认本地运行。只有你主动启用外部 LLM、Google Sheets 或招聘网站请求时，相关数据才会发送到对应服务。

## 🌍 隐私、安全与发布说明

JobsFlow 只有一套产品代码、规则和状态机。`JobSearch_2026/` 不是另一条代码或规则线，而是直接运行这套产品的一个本地实例，用来保存你的简历、搜索词、JD、评分、台账和产物。这些运行数据默认被 Git 忽略；GitHub 发布的是同一套产品代码和空模板，不包含个人资料。

首次使用由 `/setup` 根据用户的简历、求职意向、行业和限制条件生成搜索词、评分权重、方向表头与材料策略。模型可以提出公司/行业研究摘要和更贴近岗位的表头，但必须经过结构校验；缺少研究来源或模型能力不足时，系统使用可审计的通用回退，不会把法律/合规当成默认行业，也不会编造经历、数字或公司事实。

为了让能力相对有限的模型也能稳定工作，关键步骤由确定性代码兜底：JD 硬要求与薪资问询 preflight、两段评分门槛、公司研究来源检查、证据映射、材料覆盖度与 PDF 导出检查都不能被模型跳过。能力更强的模型只会提升研究和措辞，不改变这些安全边界。

准备发布或贡献前运行：

```bash
python3 setup.py --doctor-json
python3 tools/security_guards.py
python3 tools/public_release_check.py --source
pytest -q
```

发布卫生、历史清理和可复现检查见 [PUBLIC_RELEASE.md](PUBLIC_RELEASE.md)；完整的安全边界与运行规则见 [docs/system_rules.md](docs/system_rules.md)。提交前请确认 `python3 tools/public_release_check.py --source` 通过，并只发布干净快照，不要把个人工作区历史带入公开仓库。
