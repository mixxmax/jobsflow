# JobsFlow 统一质检基础设施建设技术手册

版本：v1.0
日期：2026-08-16
用途：交给没有接触过 JobsFlow 的外部大模型，独立建设“流程遵循、模型准入、材料质检、观测回溯”基础设施。
状态：只建设基础设施，不接入当前产品主链；接入由产品维护者另行审查和实施。

---

## 1. 你要建设的是什么

JobsFlow 是一个本地优先、由大模型参与执行的求职工作流系统。它把求职过程拆成几个有明确边界的阶段：

```text
setup → scan → push（用户确认后入表）→ materials → apply（用户确认，不自动提交）
```

系统支持不同模型、不同模型平台和中途换模型。模型可以负责理解、规划和生成文字，但不能自行改变业务规则、状态迁移、文件边界或用户确认要求。

本任务不是重新实现 JobsFlow，也不是重新实现材料制作，而是建设一层独立的质量控制基础设施，使系统能够回答：

1. 模型是否按规定入口和 SOP 执行？
2. 是否发生了非法状态迁移或未授权副作用？
3. 换一个模型后，是否仍能完成同一任务？
4. 生成的 CV/CL 内容是否满足 JD 定制和材料规则？
5. 发生失败后，能否知道失败在哪一步、由什么模型造成、是否可以从断点恢复？

最终目标是：新模型先经过统一验收；每次运行有轻量硬门；材料内容有独立质检；所有结果可以回放和比较。

## 2. 必须遵守的边界

### 2.1 产品线与私人线

- 产品线是仓库根目录 `/Users/xiezhijie/ai-job-search`。
- `JobSearch_2026/` 是私人运行实例，不是开发分支，不是测试数据仓库。
- 不得读取、复制、索引或提交 `JobSearch_2026/` 中的简历、JD、tracker、个人配置和材料。
- 不得把真实候选人姓名、邮箱、电话、工作经历或真实 JD 写进测试 fixture。
- 所有测试使用合成数据，或经过明确脱敏的最小样本。

### 2.2 不得修改的范围

在基础设施阶段，禁止修改：

```text
tools/workflow/
JobSearch_2026/
.claude/commands/
真实 tracker、真实 JD 缓存、真实材料
```

不得把质检器接到现有 gateway、状态机或材料主链上。不得删除或替换现有流程。

### 2.3 允许新增的范围

建议使用独立 worktree 和分支：

```text
分支：codex/quality-control-foundation
worktree：.worktrees/quality-control-foundation
```

允许新增或修改：

```text
quality_control/
tests/quality_control/
docs/quality_control/
pyproject.toml 或独立 requirements-qa.txt
```

如果仓库当前已经存在同名目录，先停下来报告，不要覆盖。

### 2.4 质检器不是第二套业务系统

质检器只能观察、记录、评分和给出 verdict。默认只读，不得：

- 直接写 tracker；
- 直接生成或修改 CV、CL、Email、DOCX、PDF；
- 直接推进 JobsFlow 状态；
- 代替 gateway 执行 `/scan`、`/push`、`/materials` 或 `/apply`；
- 在失败后无限重试；
- 用自己的状态机复制 JobsFlow 的状态机。

质检发现问题后，只能输出结构化 finding 和建议动作，交由后续适配层决定是否阻断。

## 4. 目标架构

```text
合成任务案例 / 模型矩阵
          │
          ▼
   Quality Runner
          │
          ├── JobsFlow Adapter（未来接入，当前只提供接口和 fake adapter）
          ├── Deterministic Evaluator（状态、文件、哈希、副作用）
          ├── Semantic Evaluator（可选，CV/CL 内容）
          ├── Model Switch Evaluator（接管和恢复）
          └── Trace Sink（本地 JSONL，外部平台可选）
          │
          ▼
   Assertion Results → Verdict → Report / Replay Bundle
```

核心库和 JobsFlow 适配层必须分包：

```text
quality_control/core/       # 不知道 JobsFlow 业务细节
quality_control/adapters/   # 未来知道 JobsFlow 事件和产物
quality_control/runners/    # Promptfoo/Inspect AI/本地运行器
quality_control/evaluators/ # 确定性和语义评估器
quality_control/observability/
quality_control/fixtures/
quality_control/schemas/
```

核心库只能依赖自己的 schema 和接口。 `quality_control/adapters/jobsflow.py` 可以定义接口，但在基础阶段只能使用 fake/synthetic 实现。

## 5. 核心数据契约

所有对象必须有 JSON Schema 或等价的严格校验。未知字段可以保留，但缺少必需字段必须 fail closed。

### 5.1 模型描述

```json
{
  "provider": "example",
  "model_id": "example-model",
  "harness": "cli|api|desktop",
  "model_version": "optional",
  "capability_profile": "optional",
  "temperature": "optional"
}
```

### 5.2 运行记录

```json
{
  "run_id": "qa-20260816-0001",
  "case_id": "materials-happy-path-001",
  "workflow_version": "synthetic-v1",
  "rules_digest": "sha256:...",
  "model": {},
  "started_at": "...",
  "ended_at": "...",
  "stages": [],
  "input_hashes": {},
  "output_hashes": {},
  "side_effects": [],
  "assertions": [],
  "verdict": "pass|warn|fail|blocked|error"
}
```

### 5.3 工作流事件

事件至少支持：

```text
run_started
stage_started
stage_completed
stage_blocked
model_invoked
model_switched
artifact_created
artifact_changed
audit_started
audit_completed
reset_requested
run_completed
```

事件必须包含 `run_id`、`stage`、时间、来源、输入/输出哈希和可脱敏的错误码。禁止写入 cookie、token、完整私人路径和完整 JD。

### 5.4 断言结果

```json
{
  "assertion_id": "STATE-001",
  "category": "state|sop|artifact|side_effect|semantic|performance",
  "severity": "P0|P1|P2|info",
  "status": "pass|fail|skip|not_applicable",
  "message": "",
  "evidence": [],
  "remediation": "",
  "blocking": true
}
```

不要让自由文本成为唯一真相。机器必须能够按 `assertion_id`、`status`、`severity` 聚合结果。

### 5.5 接管包

模型切换时生成：

```json
{
  "handoff_id": "handoff-...",
  "run_id": "qa-...",
  "current_stage": "materials",
  "allowed_next_actions": ["submit_plan", "submit_draft"],
  "forbidden_actions": ["scan", "push", "reset_without_confirmation"],
  "task_packet_hash": "sha256:...",
  "canonical_draft_hash": "sha256:...",
  "open_findings": [],
  "previous_model": {},
  "new_model": {}
}
```

新模型必须返回 `takeover_ack`，确认它理解阶段、输入、未解决问题和允许动作。确认失败时不得继续。

## 6. 必须实现的评测层

### 6.1 确定性 SOP 评测器

第一版优先实现，不需要调用 LLM：

- 入口是否是统一 gateway；
- 是否按合法顺序推进阶段；
- `/scan` 是否没有生成材料；
- 未经用户确认是否没有 push 入表；
- `/materials` 是否绑定岗位包；
- 是否先 plan 后 draft；
- 是否调用规定的独立 CV/CL 审计；
- 是否在最大审计轮次后停止；
- 是否保留失败产物和错误原因；
- 是否出现越权文件、非法目录或旧入口调用；
- 输入或产物变更后，旧 verdict 是否失效；
- 失败时 refresh cursor、tracker 和其他副作用是否保持不变。

确定性评测器的结果优先级高于模型自报的“已完成”。

### 6.2 材料语义评测器

只针对 CV/CL 的文字内容，不负责格式：

- JD 主要职责和硬要求是否得到回应；
- 是否符合 STAR 的基本结构；
- 是否遵守 LLMO 证据排序和位置规则；
- CV/CL 是否从对应基础版出发，避免无理由缩减核心证据；
- 职位名、雇主名和招聘机构识别是否正确；
- 是否存在残句、模板残留、内部提示词、评分或审计信息；
- 是否主动暴露候选人缺点或未要求的负面信息；
- CV/CL 之间的职位、雇主、数字、时间和语言表述是否一致；
- Cover Letter 匹配段是否简洁、具体、有岗位需求—个人证据—价值关系；
- 是否出现空泛公司赞美或未经核实的公司事实。

语义评测器只能返回 finding，不得直接改写材料。主模型负责修改，系统负责重新审查。

### 6.3 产物和格式评测器

这部分属于机械门，不属于 CV/CL 子 Agent：

- DOCX/PDF 是否由统一 renderer 生成；
- 页数、文字层、文件名、元数据；
- PDF 是否与 DOCX 内容对应；
- 是否存在空文件、错误扩展名或错误目录；
- 版式、字体、颜色和留白是否符合基础版模板。

基础质检工程只定义接口，不要复制现有 renderer 或重新实现格式引擎。

## 7. 质量级别和触发策略

### 7.1 普通运行

每个阶段执行轻量确定性检查。只有 CV/CL 文本变化时，触发一次独立内容审计。

### 7.2 模型中途切换

执行接管检查：

1. 新模型读取 handoff packet；
2. 返回 takeover_ack；
3. 校验状态和输入哈希；
4. 只允许执行剩余步骤；
5. 如果修改 CV/CL，重新触发内容审计；
6. 如果未修改受影响产物，不重跑前置扫描和评分。

### 7.3 新模型准入

新模型或模型版本变化时，运行完整合成案例矩阵，至少覆盖：

```text
正常流程
plan 缺失
职位名需要确认
已有旧产物
非法状态恢复
审计发现 P1
审计修复后复审
中途换模型
失败断点恢复
无副作用失败
```

准入结果必须按模型保存，但不能保存私人材料内容。

### 7.4 失败和循环控制

- 审计最多三轮；
- 同一 finding 连续出现两次，标记 `audit_loop_detected`；
- 外部模型调用有超时和 token 预算；
- 失败后默认停止，不自动扩大权限或改变入口；
- 质检器本身失败时不能伪造 `pass`；
- 评测框架异常和业务不合规必须区分为 `error` 与 `fail`。

## 8. 合成 fixture 设计

fixture 目录不得包含真实个人信息。每个案例由以下文件组成：

```text
fixtures/cases/<case_id>/
├── scenario.json
├── profile.json
├── jd.md
├── baseline_cv.json
├── baseline_cl.json
├── expected_events.json
├── expected_assertions.json
└── forbidden_side_effects.json
```

`scenario.json` 至少描述：

- 用户动作；
- 允许的入口；
- 预期阶段；
- 模型可能的错误行为；
- 预期 blocker 或 verdict；
- 是否允许模型切换。

fixture 必须同时包含通过案例和反例。只测试 happy path 不能证明系统安全。

## 9. 运行器和外部工具适配

### 9.1 最小运行器

先实现不依赖第三方平台的本地 runner：

```bash
python -m quality_control run --case fixtures/cases/... --model fake
python -m quality_control report --run-id ...
python -m quality_control replay --run-id ...
```

### 9.2 Promptfoo 适配器

Promptfoo 适配器负责：

- 配置模型矩阵；
- 调用外部模型或 CLI；
- 将模型输出转为 `WorkflowEvent`；
- 执行断言；
- 输出标准报告。

不得让 Promptfoo 绕过 JobsFlow gateway，也不得让 Promptfoo 直接写真实 tracker 或材料目录。

### 9.3 Inspect AI 适配器

仅在需要测试多轮工具调用和隔离文件环境时实现。默认使用临时工作区，每个案例独立，案例结束后销毁。

### 9.4 语义评测适配器

DeepEval 或 TruLens 只能实现为可选 provider。没有 API key 时，必须使用 fake judge 或跳过，并明确标注 `skip`，不能伪造通过。

### 9.5 Trace 适配器

第一版必须实现本地 JSONL sink。Opik、Langfuse 或 Phoenix 只能作为可选 sink。每条 Trace 必须经过脱敏，禁止上传私人资料。

## 10. 与 JobsFlow 的未来接入点

基础设施阶段只定义以下适配器接口，不接入真实代码：

```python
class WorkflowAdapter(Protocol):
    def snapshot(self, run_id: str) -> WorkflowSnapshot: ...
    def events(self, run_id: str) -> Iterable[WorkflowEvent]: ...
    def artifacts(self, run_id: str) -> Iterable[ArtifactRef]: ...
    def side_effects(self, run_id: str) -> Iterable[SideEffect]: ...

class ModelAdapter(Protocol):
    def invoke(self, task: ModelTask) -> ModelResponse: ...

class SemanticEvaluator(Protocol):
    def evaluate(self, material: MaterialText, context: AuditContext) -> EvaluationResult: ...
```

之后由产品维护者逐步在 JobsFlow 中接入：

1. gateway 入口事件；
2. 状态迁移事件；
3. 模型调用事件；
4. 材料 canonical draft 事件；
5. CV/CL 子审计事件；
6. DOCX/PDF 机械检查事件；
7. 最终 `apply_ready` 判定。

接入必须通过 feature flag：

```text
off       不运行质检
observe   记录但不阻断
warn      输出警告
enforce   对确定性 P0/P1 规则阻断
```

默认先使用 `observe`，经过合成案例和求职线试用后，再逐步开启 `enforce`。

- 不允许任意命令执行；
- 临时目录和 fixture 边界明确。

## 12. 性能和资源要求

质检工程不能把每次材料制作变成重新跑一遍完整系统：

- 普通确定性检查应为秒级；
- 不改变的阶段不得重复评测；
- 模型切换只检查接管包和受影响阶段；
- 语义审计只在 CV/CL 文本变化时触发；
- 外部平台调用应缓存输入哈希和规则版本；
- 多个互不依赖的模型准入案例可以并行；
- 单个案例达到预算后停止并报告，不无限等待；
- 观测记录默认本地，上传平台必须显式开启。

报告必须分别统计：模型耗时、质检耗时、外部网络耗时、token、重试次数和返工轮次，不能把所有时间都归为“模型慢”。

## 13. 外部 LLM 的执行顺序

外部 LLM 必须按以下顺序执行：

1. 检查当前分支和 worktree；
2. 读取本手册和列出的产品规则文件；
3. 只读检查当前代码，建立接口清单；
4. 创建独立 `quality_control/` 基础设施；
5. 先实现 schema、事件、断言和本地 runner；
6. 编写合成 fixture 和反例；
7. 加入 Promptfoo/Inspect AI/语义评测的可选适配器；
8. 加入本地 JSONL Trace；
9. 运行单元、集成和安全测试；
10. 生成架构说明、接入说明和未完成清单；
11. 停止，不修改 `tools/workflow/` 和 `JobSearch_2026/`；
12. 输出变更清单、测试结果、风险和建议的下一步接入点。

任何时候发现需要修改现有 JobsFlow 主链才能继续，必须停止并报告，不得自行接入。

## 15. 验收标准

基础质检工程只有满足以下条件才算完成：

1. 不读取或写入 `JobSearch_2026/`；
2. 不修改现有 `tools/workflow/` 主链；
3. 没有真实个人数据进入 fixture、日志和报告；
4. 没有外部 API 时，核心测试全部可以运行；
5. 能发现非法入口、非法状态、未授权副作用和缺失产物；
6. 能对同一案例运行不同模型并输出可比较结果；
7. 能模拟中途换模型并检查接管包；
8. 能限制审计轮次和重复 finding；
9. 能回放一次失败运行；
10. 质检器失败时不会伪造 `pass`；
11. 语义材料审计明确只覆盖 CV/CL 内容；
12. 没有把 PDF、Email、排版检查错误地交给 CV/CL 子 Agent；
13. 所有修改都集中在独立分支/worktree；
14. 输出完整测试报告和未接入清单。

“基础设施测试通过”不等于“已经接入 JobsFlow”。接入必须由产品维护者另行审查、逐步启用并在产品线测试。

## 16. 给外部 LLM 的简短任务指令

你正在建设 JobsFlow 的独立质量控制基础设施，而不是修改 JobsFlow 本身。请严格遵守本手册：只在独立分支/worktree 中新增 `quality_control/`、合成 fixture 和测试；不得读取或修改 `JobSearch_2026/`、`tools/workflow/`、真实 tracker、真实 JD 和真实材料。你必须实现事件、断言、verdict、运行器、回放、模型切换接管、审计轮次限制、本地 Trace 和可选评测适配器。先实现与 JobsFlow 无关的核心接口，再提供 fake JobsFlow adapter；不要复制状态机，不要直接执行真实业务命令，不要写真实产物。完成后只提交代码、测试、架构文档、接入契约、风险清单和测试结果；如果发现必须修改主链才能继续，立即停止并报告。
