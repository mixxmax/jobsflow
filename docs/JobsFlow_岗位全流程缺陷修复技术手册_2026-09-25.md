## P0-1　票据 handoff 兑换路径不可达（3.7）

**事实**

- `tools/workflow/sopcontrol_adapter.py` 的 `admit`（约 824-838 行）：只要 `ticket_id` 或 `secret` 缺一个，就**重新签发一张票**并停下。
- `_redeem_capability_ticket`（约 693-729 行）里写了"只有 id 时从 0600 handoff 文件读取 secret"的回退逻辑，但 admit 只有在 id 和 secret 同时存在时才会调用它，因此这段回退**永远不会执行**。
- 用户提示 `interaction_shell.py:506` 告诉调用方"回传 capability_ticket_id；secret 经 0600 handoff 兑换"，而这条路实际走不通。`tests/test_interaction_shell.py:404-428` 名义上测试"retry 仍可经 handoff 兑换"，实际只断言了 secret 被脱敏。

**修复**

1. 在 `admit` 中改分支条件：
   - 无 `ticket_id` → 签发新票（保持现状）。
   - 有 `ticket_id` → 一律走 `_redeem_capability_ticket(request)`（它会在缺 secret 时读取 handoff）。
   - 有 id、handoff 文件不存在或已被消费 → 返回明确的 blocker `capability_ticket_handoff_missing`，**不要**悄悄再签一张新票（否则调用方会陷入无限的签票循环）。
2. `load_capability_handoff_secret(..., consume=True)` 读取后删除文件的行为保持不变（一次性）。
3. 核对 handoff 文件中记录的 `action`/`run_id` 与请求一致；不一致按 `capability_ticket_invalid` 处理。

**测试（开启票据）**

- 第一次调用 → `planned`，零副作用，生成 0600 handoff 文件，stdout 中无 secret。
- 仅带 `--capability-ticket-id` 重试 → 兑换成功并执行；handoff 文件被删除。
- 用同一个 id 再重试 → `capability_ticket_handoff_missing` 或 `capability_ticket_invalid`，零副作用，**不签发新票**。
- 改写 `test_interaction_shell.py:404-428`，让它真正断言兑换成功。

## P0-2　produce / batch 同一张票被重复兑换（3.2）

**事实**

- `tools/workflow/__main__.py:1004-1022` 的 produce 循环对每个阶段执行 `step_payload = dict(payload)`，把同一对 `capability_ticket_id/secret` 传给每一次 `dispatch`。第一阶段消费掉这张票，第二阶段必然报 `capability_ticket_invalid / TicketError`，`produce_should_stop` 随即停止。**在 enforce 模式下，produce 永远过不了第一阶段。**
- 票据指纹（`_ticket_fingerprint`，约 513-538 行）绑定的是 action、binding、run_id、job_id，**不含 stage**，所以不能靠"每阶段一张不同指纹的票"来区分阶段。
- `tools/workflow/materials_batch.py:180-195` 的 `_one` 重建 payload 时只带 `job_id/stage/materials_engine`，不带票据字段，于是内层每次 dispatch 都只签发新票、返回 `planned`；而 `run_batch`（约 226 行）只把 `blocked/failed` 算作失败，**什么都没做也报 `succeeded`**。这违反 JF-MAT-105 的"不得伪造通过"。
- 没有任何测试让 produce 在开启票据的情况下走完整链。

**设计决定（回答原简报评审问题 2）**

采用"**每个副作用一张票，同一次已授权的复合命令内由宿主在进程内接力**"：

- 用户（或调用方）只需兑换复合命令（produce 或 batch）的**第一张票**；这证明用户授权了本次命令。
- 之后每个阶段仍各自签发、各自兑换一张独立的票，因此每一个副作用都有自己的回执，审计粒度不变。
- 接力只能在同一进程、同一次命令调用内发生，secret 不离开内存，不写 stdout。接力的前提是本次调用的第一张票已由调用方成功兑换，模型无法凭空触发接力。
- 跨命令、跨会话仍要求重新取票。**不要**实现"会话级长效票"。

该模式与 scan 现有的 `maybe_auto_redeem_scan`（`engine.py:429-453`）一致，可参照实现。

**修复**

1. 把 produce 循环从 `__main__.py` 抽到库模块（如 `tools/workflow/materials_produce.py`），CLI 只调用它，Python API 调用方共用同一实现。
2. 新增辅助函数 `dispatch_with_relay(action, payload, *, relay_allowed: bool)`：
   - 用不带票据字段的 payload 调用 `dispatch`；
   - 若返回 `planned` 且 `requires_capability_ticket`，并且结果中的 `job_id` 和 action 与本次请求一致，就用结果中进程内的 `capability_ticket_id/secret` **立即再 dispatch 一次**；
   - 之后删除签发时写出的 handoff 文件（调用 `load_capability_handoff_secret(..., consume=True)` 或直接 unlink）；
   - 从返回值中剥掉 secret，并追加 `ticket_relay: [{stage, ticket_id}]` 供审计。
3. produce 流程：
   - 第一阶段用调用方提供的票据 dispatch。返回 `planned`（需要票）时原样返回给用户，不接力。
   - 第一阶段成功后，其余阶段一律走 `dispatch_with_relay(..., relay_allowed=True)`。
   - 接力次数上限 = 计划阶段数 − 1；遇到 `blocked/failed` 或任一 `PRODUCE_STOP_BLOCKERS` 立即停止。
4. batch：
   - 外层 `materials batch` 兑换成功后，`_one` 内每个 dispatch 都走 `dispatch_with_relay(..., relay_allowed=True)`。
   - 每个岗位的各阶段仍严格串行，最多 3 个 worker（JF-MAT-105）。
   - `run_batch` 的汇总规则改为：任一结果为 `planned`、`needs_user` 或带 `capability_ticket_required` 的，都不得算作成功，整体报 `partial` 或 `blocked`，并列出这些岗位。
5. `_write_path_requested`：当 `stage == "batch"` 且 `batch_action == "status"` 时返回 False，只读状态查询不应要求票据。

**测试（开启票据，合成包，渲染与审计提供方用桩）**

- 从 `plan_ready` 出发：produce 首次调用 → `planned`，零副作用；带票重试 → canonical、audit、render、pdf、format 依次执行；每个阶段有一张不同的已消费票；输出中无 secret；handoff 目录里不残留文件。
- 伪造或已用过的首票 → `blocked`，不发生任何接力，零副作用。
- 中途某阶段 `blocked` → 停止，其后不再签票。
- batch：2 个岗位，外层带票 → 两个岗位都实际执行；把其中一个岗位的内层返回改成 `planned` 的桩 → 汇总不是 `succeeded`。
- batch status 不要求票据。

## P0-3　包准备没有入口（3.1）

**事实**

- `/push` 与 intake 只调用 `create_package_from_entry_row`（`tools/job_materials/packages.py:253-333`），写出 4 个文件：`job_snapshot.md`、`tracker_row.json`、`job_manifest.json`、`package_binding.json`。
- 材料门 `tools/workflow/package_context.py` 需要三样东西：JD 全文（约 142-147 行）、与 JD 哈希一致的评估（约 233-244 行）、`application_preflight.json`（约 246-249 行）。vNext 的 `bundle.py:158-161` 会把这些 blocker 全部作为硬拦截。
- 能写这些文件的只有 `tools/job_materials/__main__.py` 的 `cmd_jd / cmd_preflight / cmd_tailor / cmd_enrich`，而它们在 d0bef50（2026-09-08）被列入 `_gateway_blocked`（约 1227-1241 行）。gateway 从不生成这些文件。
- **`read_jd` 会把快照误当成 JD**：`tools/job_materials/jd_store.py:48-66` 在 `jd_full.md` 缺失时，只要 `job_snapshot.md` 含有 "JD" 字样就返回整个快照。而生成器写出的快照里固定含 "JD"（`packages.py:246-247` 的提示文字），所以代码永远走不到 `02_Tracker/jds/{pid}.md`。快照有 400 多字符，`jd_meta` 会把它判为 `ok` 深度，于是不报 `missing_full_jd`，最终表现为评估哈希不匹配。
- scan 写的 JD 缓存有两种：
  - URL 键缓存 `02_Tracker/jds/cache/<sha16(url)>.json`，由 `tools/fresh_24h/jd_cache.py` 写入；
  - `_persist_deep_jds`（`two_pass_score.py:1770-1791`）写出的文件以 `preview-*` 命名（2019-2020 行在写之前把 `岗位编号` 清空了），永远对不上 `jds/{job_id}.md`，而且路径被硬编码为 `repo/JobSearch_2026/...`。
- 快照里的提示文字指引用户执行 `python3 -m tools.job_materials jd set`，而这个命令已被封禁。

**修复**

1. **新增 gateway 一等阶段 `materials prepare`**（CLI：`python3 -m tools.workflow materials prepare --job-id X [--jd-file F] [--refresh]`）。它属于写动作，需要票据，并适用 P0-2 的接力规则。全程确定性，不调用 LLM：
   1. 用 `PackageContextLoader` 定位包，从 manifest、`tracker_row.json`、快照中解析规范 URL。
   2. JD 来源优先级：已有 `jd_full.md`（除非 `--refresh`）→ `--jd-file`（文本 ≥ `FULL_JD_MIN_CHARS`）→ `load_jd_cache(url, workspace)` → `02_Tracker/jds/{job_id}.md`。全部落空时返回 blocker `jd_full_unavailable`，`next_action` 提示用 `--jd-file` 提供全文，或走 §P1-4 的有界抓取。
   3. 调用 `write_jd(workspace, package, text, url=..., source="jd_cache:<原 source>" | "user_file")`。
   4. 评估：计算 `jd_fingerprint(text)`。若 `_latest_assessment` 按身份和哈希找到匹配记录，直接复用；否则用与 intake `_score_row` 相同的确定性深评路径（`score_job(..., jd_depth="deep")` 加现有的评估记录写入器）生成一条新评估，`job_id` 填持久编号。**不写 tracker**；分数变化写在输出里，需要更新表格时另走 sync gateway。
   5. preflight：把 `_known_application_answers` 从 `tools/job_materials/__main__.py` 移到库模块（如 `requirements_engine.py` 或新建 `preflight_inputs.py`），再调用 `build_application_preflight(...)` 和 `write_application_preflight(...)`。**gateway 不得 import `tools.job_materials.__main__`。**
   6. 幂等：记录输入哈希（JD、profile、已知答案），输入不变时重跑为 no-op。
   7. 返回 `after_state` 和剩余 blocker，例如 `unresolved_hard_requirement` 就交给用户处理。
2. **接入主流程**：
   - produce 或 run 从 `idle/inputs_frozen` 出发时，若 context blocker ⊆ {`missing_full_jd`, `assessment_missing_or_stale`, `preflight_missing`}，先执行 `prepare` 阶段，再执行 `plan`。把 prepare 加进 `next_produce_stages` 的相应阶段。
   - `materials batch --batch-action prepare` 改为依次执行 `prepare` 与 `plan`（目前只调 plan）。
   - `/push` **不**自动调用 prepare，保持"入表不制作材料"的边界。
3. **修 `read_jd`**：快照不再按 "JD" 关键字被接受。只有当快照含有显式的全文 JD 段落，且正文 ≥ `FULL_JD_MIN_CHARS`、不含生成器的占位提示时，才接受快照；否则继续查 `jds/{pid}.md`，最后返回空。先 `grep` 测试夹具和旧包格式，确保兼容历史上把 JD 粘进快照的包。修复后，骨架包会如实报 `missing_full_jd`，并由 prepare 解决。
4. **修 `_persist_deep_jds`**：根目录改用传入的工作区参数，不再硬编码 `repo/JobSearch_2026`；同时确保每条深评 JD 都写进 URL 键缓存（`save_jd_cache`），这样 prepare 能按 URL 找到它。先确认深评路径（约 544 行）是否已对所有门户写入 URL 缓存，只补缺的部分。
5. 快照提示文字（`packages.py:246-247`）改为指向 `python3 -m tools.workflow materials prepare`。
6. **治理守卫**：新增一条 import 图测试，断言 `write_application_preflight` 和 `write_jd` 的生产调用方只有 gateway 的 prepare 与已退役的 `job_materials` CLI。这样可以防止再出现"CLI 封了、函数层敞开、实际靠进程内调用"的状态。同步更新 `docs/materials_vnext.md` 与 `.claude/commands/materials.md`。

**测试**

- 合成骨架包 + URL 缓存 → prepare 后三个 blocker 全部消失；再跑一次是 no-op。
- 无缓存、无 `--jd-file` → `jd_full_unavailable`，零写入。
- 骨架快照不再被 `read_jd` 当作 JD（反例）。
- 评估已存在且哈希匹配 → 复用，不重新评分；JD 改变 → 生成新评估。
- produce 从 idle 出发 → 自动先执行 prepare。

## P0-4　CDP 附接超时单位陷阱与浏览器端点（2.1）

**事实**

- 工作区修复 `_cdp_connect_timeout_ms()`（`portal_jd_browser.py` 约 1440-1455 行）按**毫秒**读取 `JOBSFLOW_JOBSDB_CDP_CONNECT_TIMEOUT`，而同一文件里的 `JOBSFLOW_JOBSDB_CDP_STARTUP_TIMEOUT`（约 2274-2285 行）按**秒**读取，两者默认值都写作 30。用户按秒填 `=30` 会被夹成 1 秒，比原来的 5 秒还短，而且没有任何提示。`nan` 和 `inf` 会被夹到 120000。
- ws-only 模式下，`_cdp_ws_connection_url`（约 1292-1305 行）构造的是不带 GUID 的 `ws://host:port/devtools/browser`；仓库中没有任何代码读取 Chrome 的 `DevToolsActivePort`。Chrome 的浏览器端点通常形如 `/devtools/browser/<guid>`，裸路径能否连通**从未在真实 Chrome 上验证过**。

**修复**

1. `JOBSFLOW_JOBSDB_CDP_CONNECT_TIMEOUT` 改为**秒**：默认 30，夹紧到 1–120，内部换算成毫秒。非数字或非有限值（nan/inf）一律回退默认值。把实际生效值写进附接诊断（只记数字，不记端点凭据）。同步更新 AGENTS.md 和 README 中的环境变量说明，并在 docstring 里写明单位。
2. 测试改为：`"30"` → 30000ms；`"0.5"` → 1000ms；`"500"` → 120000ms；`"nan"`、`"inf"`、`"abc"` → 30000ms；未设置 → 30000ms。另保留"配置值传入 `connect_over_cdp`"的测试。
3. 端点解析顺序：显式 `JOBSFLOW_JOBSDB_CDP_URL` → `DevToolsActivePort` → 裸路径。
   - `DevToolsActivePort` 文件第 1 行是端口，第 2 行是 `/devtools/browser/<guid>`。默认读取 macOS 的 `~/Library/Application Support/Google/Chrome/DevToolsActivePort`；Linux 和 Windows 用对应的默认用户数据目录；允许用新环境变量 `JOBSFLOW_JOBSDB_CHROME_USER_DATA_DIR` 覆盖。
   - 只有当文件中的端口等于配置的端口时才使用，并且结果仍须通过 `_validate_local_cdp_endpoint`（仅限本地地址，路径以 `/devtools/browser` 开头）。
   - 只读这个文件，**绝不**启动浏览器、绝不写任何浏览器文件。

## P1-2　初评硬淘汰、teaser 判据与 repost（1.1）

**事实**

- `docs/system_rules.md:165` 规定初评分"只用于排程深评"；`:237-239` 规定"不得硬淘汰信息贫乏卡，应保留为显式的待审项"。实现与文档冲突，defer 模式和非 defer 模式都有这个问题。

- 1993 行打印的救回下限始终用 `gate_pass1` 计算，defer 模式下显示错误。

**设计决定（评审问题 1）**：不在初评阶段淘汰，只做排序和深评调度。这正是 system_rules 的现行规定，本条是让实现符合文档，不是新政策。如果所有者选择保留淘汰，就必须同步修改 system_rules，二者不能继续不一致；**执行者应先向用户确认这一点再动手**。

**修复**

1. **不再静默丢弃**：未被救回的行保留在评分产物中，`评估状态 = pass1_low_priority`、`层级 = 待审-初评偏低`，不分配深评预算，排在最后。
   - 默认 push 预览可以折叠这一层（只显示数量，另提供展开开关），但这些行必须能被 `push --select` 选中。选中后走现有的 `deepen_scored_rows` 深评。
   - `pass1_dropped` 等诊断计数改名或补充为 `pass1_low_priority`。
   - 先核对 push 预览、归档、清理等消费方对新层级的处理，确保它们不会被自动入表（JF-SCAN-001）。
2. **teaser 信息量判据语义化**：在 `policy.py` 增加 `teaser_is_informative(teaser, title) -> bool`。
   - 先剔除通用招聘套话（放在跟踪仓库里的**通用**模式表，例如 "competitive remuneration"、"attractive package"、"we offer"、"fringe benefits"、"interested parties"、"apply now"、"5-day work"、"medical insurance"、"career development"，以及中文里的"待遇优厚""五天工作""有意者"等）。
   - 剩余文本满足两个条件才算有信息：去空白后 ≥ 60 字符，且包含至少 N 个职责或技能信号词。信号词取自运行时 scoring profile 的关键词加一组通用职责动词。**不得**把任何私人关键词硬编码进跟踪仓库。
   - `thin_teaser = not teaser_is_informative(...)`；1243-1248 行的网络优先级计算也改用这个函数。
3. **repost 只提示、不压制**：
   - 跨轮历史中出现规范化后相同的"公司+标题"但编号不同 → 在该行加 `possible_repost_of=<先前 URL 或编号>`，并在预览中显示，不从结果中移除（不同编号可能是真实的不同职位，这是现有注释明确顾虑的）。
   - push 时若账本中已有相同的规范化"公司+标题"，在预览中给出 `possible_duplicate_of=<job_id>` 警告，由用户在确认时决定。
4. 修 1993 行：打印实际使用的 `retrieval_floor`。

**测试**：广告套话 teaser（≥ 60 字符）被判为信息贫乏；真实职责 teaser 被判为有信息；低分行保留在产物中且可被 `--select` 选中；低分行不会自动入表；repost 行被标注但未被移除。

## P2-2　语义 lint 误报与 JD 动词（3.5）

**事实**

- `semantic_lint.py:426-457`：只要同一块里出现了某种语言，块内任何位置出现的级别词都算作该语言的级别（"worked with business teams" 中的 business 会被当成级别）。该发现为 P1。

**修复**

1. 级别词只在紧邻语言的位置才生效：例如 `<level> <language>`、`<language> (<level>)`、`<language>: <level>`，或窗口 ±2 词以内且中间没有其他名词。测试：`business teams … English` 不报；`Business English` 对比 `Native English` 要报。
2. `verb_escalation` **不**把 JD 原文动词加入允许集。允许集 = 基线动词 ∪ 候选人事实库中已核实的、属于该段经历的证据动词。对 JD 中出现过的升级动词，仍然拦截，但发现中带 `jd_anchored: true`，`required_action` 给出两条路：
