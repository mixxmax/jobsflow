# 材料制作：第二轮修复与外部验收

范围：仅本地产品线。运行实例直接执行产品代码，不复制规则或部署另一套脚本。
没有修改私人岗位包、访问真实招聘门户、写入 Google Sheets 或执行投递。
本轮不 commit/push；第一轮未提交修改及原有无关文件完整保留。

## 修复内容

1. **完整短 JD 不再靠凑字数过门。** prepare、intake、全文获取助手、缓存和
   JD 存储共用正文判断。已验证页面全文或用户明确确认的短正文可用；确认绑定正文
   SHA256，并随包与 tracker 镜像保留。缓存仍受有效期控制。没有依据的短文本、验证页
   和占位符不会因门户名称或 `jd_complete="false"` 这种真值陷阱而放行。标题、公司、
   薪资等前置元信息不计入正文长度启发式。正文自身的 Markdown 分隔线不能截掉前半份 JD。
2. **返回当前岗位的来源清单。** 缺 JD 时输出有界 `jd_sources`：当前包、当前 URL
   缓存和当前编号镜像的路径、长度、哈希与可用性。不读取其他岗位材料，也不把原文反复
   打印给模型。完整性确认命令带实例路径及预期正文哈希；正文变化后旧命令失效。
   模型不得把该命令当作自动重试；先取得用户确认或已有页面全文验证依据。
3. **基础版换行贯穿全链。** Word 软换行保留到 baseline、canonical、主模型任务包、
   子审计任务包和 DOCX。多条目块提供 `logical_items`，使用现有 bounded replace
   对完整条目有限改写或排序，无需新造全份 JSON，也不需要新增加一套制作入口。
   渲染器对每行重复基础版的标签/正文样式；格式门使用同一逐行契约。
4. **减少无意义返工。** 旧冻结文本若已把词粘在一起，补标点或恢复条目边界不再因
   数字对象解析误报 P1；真实的计数对象替换仍拦截。独立审计、定点复审、三审上限、
   generation/正文绑定及一页格式门没有取消。
5. **前置准备也可观察。** 独立的有界计数文件记录 prepare、公司身份和 planning
   调用；进入 generation 后投影到 `materials_run.json.preparation`。包含主机耗时与
   调用间跨度，不含原文或 secret，不把等待时间算成模型推理时间，不重复累计嵌套
   auto-prepare。记录失败不改变门禁结果；更新投影时复用包锁，不能回滚流程状态。

## 验收方式

用未制作过的新岗位，以日常请求让全新模型制作材料。不要额外教内部 schema，不要
把其他包作为范例。有旧产物的岗位仍按原有 preview→用户确认→reset 规则处理。

重点观察：

- 页面全文已保存但不足 400 字时，能否通过准确的来源/确认指引继续，不补标题凑字数。
- 主模型能否直接读 returned path / logical_items，避免翻源码或其他包摸索格式。
- Core Expertise 的分项是否清楚，重要 JD 主题能否以有限改动前置。
- 独立 P1 是否有定点复核，最终 CV/CL 是否沿用基础版样式并通过机械门。
- preparation 与 generation 的耗时记录能否解释等待发生在哪里。

回传：岗位编号、起止时间、人工等待、独立审计次数/耗时、是否读取源码或其他包、
返工原因、最终状态。不要回传票据 secret 或复制候选人事实。

这些修复针对已经复现的断点；不能仅凭合成测试承诺固定的整体分钟数或特定模型表现。
已冻结的旧 generation 不会被批量重写或静默迁移。

确认目标变更、确认元信息丢失后的恢复、CLI 透传、真实 gateway 冻结包、逻辑条目
到审计任务包、真实 DOCX 渲染与格式门、数字对象误报，以及观测的并发/只读边界。
准备与渲染测试均使用合成实例；真实浏览器被测试隔离设施禁止访问。

- `sopctl gate .`：17 条正式规则核验通过，账本完整性通过。
- 没有执行全仓全量测试或真实外部模型验收；下一轮仍需由新模型验证实际体验。

## 自查后的补强（2026-10-23）

第二轮测试通过后，独立复查又发现五处跨环节缺口；因此上文的通过数只代表当时
覆盖的用例，不代表全部边界已正确。现已在同一产品代码链补强：

- 缓存读取、扫描结果和 JD 镜像携带原有完整性凭证；只有实际详情获取分支可以
  创建页面验证凭证。缓存命中、字段名或再次保存不能制造新凭证；长旧 JD 仍可按
  原长度启发式使用，但不能伪称页面已验证。全文获取助手也检查上游凭证。
- 扫描的 ID 镜像同时保存正文绑定的凭证；只剩镜像时也不要求重复确认。更换正文
  后旧凭证失效；用户确认的来源身份不能被改写成页面验证。
- 首个 generation 在创建的包锁内绑定岗位授权，后续准入只比较、不补绑。已经有
  材料版本的旧空绑定授权需要重新确认，不能借接手或重置认领另一版本。
- 授权和准备耗时记录复用 `is_assigned_job_id`，包含产品支持的三级编号；不再
  各写一套编号正则。
- 观测数据先验证结构，损坏的观察计数按不可用处理；额外的容错边界防止字段类型
  错误把成功的 JD/preflight 写入误报为业务失败。它不能替代或放松任何质量门。

新反例集中在 `tests/test_materials_review_hardening.py`，均使用合成实例及隔离的
控制器注册表。未修改私人材料、控制器规则或远端版本；仍需外部模型验收真实体验。

补强后的验证：新增反例 21 passed；授权/prepare/扫描助手/详情获取组 65 passed；
第二轮/语义 lint/intake/CLI 票据/扫描效率组 62 passed；新反例/恢复/SOP 接入/
workflow 组 52 passed；门户缓存相关选择组 6 passed。分组有重叠，不累加。
安全守卫、公开源码检查、技能检查及差异检查通过；SOP Control 正式规则与账本门通过。
