# JobsFlow 外壳交互层改进技术手册

- 状态：设计草案，尚未进入实现
- 日期：2026-09-12
- 范围：只改用户/助手看得到的停顿、默认工作区和命令表面；不改评分、门户、材料 vNext 内核、SOP 规则内容
- 不变量：fail-closed 仍在；不自动投递；私人数据仍只在运行实例；模型不能绕过网关

## 1. 决策摘要

内核已经能拦住越界。外壳的问题是：停下来之后，用户看不到选项，也不知道下一句怎么答。本次把外壳收成五件，按顺序做，前一件没验收不许做后一件。

```text
1. 工作区默认绑到私人运行实例
2. 能力票据在网关内自动兑一次，不出现在对话里
3. 凡是要人拍板，返回同一张停顿卡（问题 + 选项 + 怎么回）
4. 材料对外收成「核对 / 出稿 / 你看过再投」
5. doctor 只回答「下一步做什么」
```

用户仍通过 AI 助手或 CLI 使用，不新建 GUI、网页或设置中心。问法由网关给出，助手只朗读和回传，不得自己编选项。

## 2. 为什么改外壳，不改内核

当前能拦住的：没预览就写表、没基础版就做材料、职位歧义未确认、缺 LibreOffice 就出 PDF。

当前看起来像坏了的：

| 现象 | 根因 |
|---|---|
| 在仓库根跑 `/scan`，扫不到画像/台账 | `_workspace()` 不选择子目录 `JobSearch_2026/` |
| 第一次扫描返回 `planned` + ticket secret | `WorkflowEngine` 把 SOP 二阶段挑战直接暴露给调用方 |
| `role_confirmation_required` 没有 1/2 | 阻断码有了，选项没有进同一条结果 |
| 文件名过长用户以为要选表述 | 主机压缩文件名，但结果里没说明正文仍是全称 |
| doctor 报 `tracker: false` 且 `next_action: continue` | 检查的是产品根，不是运行实例；没有排序过的下一动作 |

这些都是表面契约，不是状态机错误。材料引擎、SOP 规则、门户恢复器保持不动。

## 3. 明确不做

- 不做 Web UI、看板、通知中心、设置页。
- 不把 fail-closed 改成警告后继续。
- 不让模型在停顿时自由发挥问法或补选项。
- 不把能力票据改成长期会话 token。
- 不把文件名过长变成用户选择题；正文和 manifest 仍保留全称。
- 不授权本次手册范围内的 commit / push。实现前另下指令。

## 4. 目标契约

所有高层动作仍只进：

```bash
python3 -m tools.workflow <action>
```

对外结果只允许三种终态：

| `status` | 含义 | 用户看到什么 |
|---|---|---|
| `succeeded` | 本步做完 | 岗位列表 / 文件路径 / 检查清单 |
| `needs_user` | 必须等人答 | 一张停顿卡，见第 7 节 |
| `blocked` / `failed` | 环境或规则硬失败 | 原因 + 一条修复命令，无假选项 |

`planned` 不再作为给用户的主状态。预览类动作（push 未确认、intent 未确认）也改报 `needs_user`，选项里带「确认 / 取消」。测试和 SOP receipt 仍可在内部记录 `planned`。

`capability_ticket_id` / `capability_ticket_secret` 默认不得出现在 CLI stdout。调试开关见 6.4。

## 5. 改动一：工作区默认绑定

### 5.1 要改什么

文件：`tools/workflow/__main__.py` 的 `_workspace()`。

当前顺序：

1. `--workspace`
2. `JOBSEARCH_ROOT`
3. cwd 名叫 `JobSearch_2026` 且有 `00_Profile` → cwd
4. 否则 cwd（产品根会落到产品根，台账检查失败）

新顺序：

1. `--workspace`（显式最高）
2. `JOBSEARCH_ROOT`
3. cwd 是运行实例（目录名为 `JobSearch_2026`，或具备 `00_Profile` + `02_Tracker`）→ cwd
4. **cwd 是产品根，且 `cwd/JobSearch_2026/00_Profile` 存在** → 该子目录
5. 否则 cwd

产品根判定（必须同时成立，防止把任意仓库当成 JobsFlow）：

- 存在 `tools/workflow/__main__.py`
- 存在 `.sopcontrol/rules/registry.yaml` 或 `setup.py`

只绑定**产品根下的规范子目录名** `JobSearch_2026`。不要扫描兄弟目录，不要按 mtime 猜最新工作区，不要把 `JobSearch_2025` 之类别名偷偷接上。

### 5.2 为什么这不等于「模型省略参数就能碰私人数据」

旧注释担心：在产品根省略 `--workspace` 会误操作私人树。规范子目录本来就是本机唯一运行实例；setup 也把实例建在这里。危险的是猜产品根**外面**的目录。新规则不猜外面。

若产品根下没有 `JobSearch_2026/00_Profile`（全新 clone、尚未 `/setup`）：保持 cwd，doctor 的下一动作必须是 `run_setup`，scan/push/materials 写路径必须因 `runtime_workspace_invalid` 失败，不得在产品根创建 `02_Tracker/`。

为此，在 `WorkflowEngine.execute` 对 `scan` / `push` / `materials` / `audit` / `format` / `apply` / `base` / `intent` / `archive_*` 调用已有的 `tools.workflow.runtime.assert_runtime_instance(workspace)`。今天该函数已存在，但没有接到网关。写动作缺运行实例标记时直接 `blocked`，`blockers=["runtime_workspace_invalid"]`，停顿卡指向 `/setup`。

`doctor` 允许在产品根运行，用来报告「还没有运行实例」。

### 5.3 doctor 与 setup 对齐

`tools/workflow/__main__.py` 里 doctor 的 `checks["tracker"]` 改为看 **已经解析出的 workspace**：

```python
checks["tracker"] = bool(list((workspace / "02_Tracker").glob("hk_apply_list_*.csv")))
```

`setup.py` 的 `doctor_snapshot()` 里硬编码 `REPO / "JobSearch_2026"` 的 tracker 检查，改为可传入 workspace；workflow doctor 把解析后的 workspace 传进去。避免两套根。

`setup.py --doctor` 在尚未 setup 时仍以 `REPO/JobSearch_2026` 为预期实例路径，这是向导自己的目标位置，与网关默认绑定一致。

### 5.4 命令文档

`.claude/commands/` 下 `scan.md` `push.md` `materials.md` `apply.md` `intent.md` 的示例命令**不要**再要求模型每次手写 `--workspace JobSearch_2026`。改成一句：

> 默认运行实例是产品根下的 `JobSearch_2026/`。只有用户指定了别的目录，才加 `--workspace`。

`AGENTS.md` / `CLAUDE.md` 的 sopcontrol 投影区不要手改；若需要补一句工作区规则，写在投影区外的产品段落，或作为新 SOP 规则走 `sopctl`（本手册不强制新增规则）。

### 5.5 测试

替换 `tests/test_workflow_workspace_boundary.py`：

| 用例 | 期望 |
|---|---|
| 产品根下存在 `JobSearch_2026/00_Profile`，cwd=产品根，无 env | 解析到该子目录 |
| 产品根下没有该子目录 | 解析到产品根；scan 写动作 `runtime_workspace_invalid` |
| `--workspace` 指向别处 | 用显式路径 |
| `JOBSEARCH_ROOT` 指向别处 | 用环境变量 |
| cwd 已在运行实例内 | 用 cwd |
| 产品根的兄弟目录也叫 `JobSearch_2026` | **不得**选中 |

`python3 -m pytest -q tests/test_workflow_workspace_boundary.py tests/test_workflow_cli_capability_ticket.py`

验收：在 `ai-job-search/` 根目录不带 `--workspace` 跑 `python3 -m tools.workflow doctor --json`，`checks.tracker` 对已 setup 的机器为 true；`materials_base` 读到 A–G 基础版，而不是空的产品根。

## 6. 改动二：能力票据内化

### 6.1 要改什么

文件：`tools/workflow/engine.py` 的 `WorkflowEngine.execute`。

当前：`admit()` 若 `ticket_challenge`，engine 立刻 `return`，`status=planned`，并把 `capability_ticket_id` / `secret` 放进结果。调用方必须再发一次。

目标：同一次 `execute()` 内完成「挑战 → 把票据写回 payload → 再 admit 一次 → 跑 adapter」。对用户这是一次 `/scan`。

### 6.2 怎么改

在现有这段之后（约 260–284 行，`if sop_admit_report and sop_admit_report.get("blocking")`）：

```text
若 ticket_challenge
  且 payload 里还没有 capability_ticket_id/secret
  且 admit 报告里有 ticket_id 和 secret：
      把 id/secret/run_id 写入 payload 与 request.payload
      不得把 secret 写入 ControlEvent detail（现有 sanitize 已红acted，保持）
      以同一 request 再走一遍 admit（不要新开 entity、不要换 run_id）
      第二次仍 blocking 且仍是 ticket → 按 blocked 返回，不再循环
      第二次 pass → 继续现有 _run_adapter
否则：保持现有 blocked 路径
```

只允许 **一次** 自动兑票。死循环用局部标志 `_ticket_autoredemeed`。

`run_id` 恢复逻辑已经在 `execute()` 前部（scan 从 ticket 恢复、push 从 proposal 恢复）。自动兑票必须发生在这段恢复**之后**，第一次 admit 就要带上将要写入的 run_id。扫描应在第一次 admit 之前生成并写入 `payload["run_id"]`（若空），这样挑战和兑现指纹一致。今天是 adapter 里才生成 `scan-{uuid}`，第一次 admit 的 fingerprint 可能和第二次不同。一并改：

- `scan`：在 admit 前，若无 `run_id`，生成 `scan-{uuid4().hex[:8]}` 写入 payload
- 自动兑票复用这个 id，不再让 adapter 另造一个

### 6.3 谁还走显式票据

保留 CLI 的 `--capability-ticket-id` / `--capability-ticket-secret`，供调试和测试直接打 adapter。默认路径不再需要。

`.claude/commands/scan.md` 删除「如果返回 capability_ticket_required，请重试并透传 secret」整段。改成：网关内部兑票；用户侧只看到扫描结果或停顿卡。

### 6.4 调试开关

仅当 `JOBSFLOW_SOPCONTROL_EXPOSE_TICKET=1` 且 `relax_allowed()` 为真时，结果里才带 ticket 字段。生产助手拿不到 secret。

### 6.5 SOP 证据

两次 admit 都要留 receipt：第一次 `outcome=ticket_required`，第二次 `outcome=admitted`。这是控制面审计，不是用户提示。

### 6.6 测试

现有会坏的用例（必须以 engine 结果为准改断言，adapter 单测仍可测挑战本身）：

- `tests/test_sopcontrol_final_integration.py`：`test_ticket_challenge_has_zero_side_effects` 改为测 **adapter.admit()** 仍 `ticket_challenge` 且无 adapter 副作用；另增 engine 级用例：一次 `dispatch("scan", ...)` 无 ticket 字段即进入 adapter（fixture 扫描除外，fixture 本来不写、不挑战）
- `test_scan_ticket_retry_recovers_bound_run_without_cli_run_id`：改为「engine 一次调用内 run_id 稳定」，不再要求调用方重试
- `tests/test_workflow_cli_capability_ticket.py`：CLI 仍能把显式 ticket 传进 payload；默认扫描 stdout 不含 `capability_ticket_secret`

验收：对本机私人工作区跑一次 dry-run 以外的 fixture scan，stdout JSON 无 secret；`sop_control_admit.verdict` 为 `pass` 或业务 blockers，而不是停在 `ticket_required`。

## 7. 改动三：停顿卡（用户选择题的唯一表面）

### 7.1 新模块

新建 `tools/workflow/user_prompt.py`，不要把格式散落在各个 adapter。

```python
PROMPT_SCHEMA_VERSION = 1

def pause(*, kind: str, question: str, options: list[dict], why: str, reply_hint: str, **extra) -> dict:
    return {
        "schema_version": PROMPT_SCHEMA_VERSION,
        "kind": kind,
        "question": question,
        "options": options,          # [{id, label, recommended, note}]
        "why_it_matters": why,
        "reply": reply_hint,         # 给用户看的一句话
        "reply_contract": extra.get("reply_contract") or {},  # 给助手的回传字段
    }
```

`kind` 固定枚举，禁止自由字符串：

| kind | 何时 |
|---|---|
| `choose_role_title` | 材料前职位歧义 |
| `select_jobs` | review-first / push 需要用户点名 |
| `confirm_push` | 入表预览已生成 |
| `confirm_intent` | 意向预览已生成 |
| `confirm_base` | 基础版激活预览 |
| `ask_preflight` | 薪资/到岗/工作权等 |
| `confirm_archive` | 归档预览 |
| `setup_required` | 还没有运行实例 |

`options` 至少一项。`recommended: true` 最多一个。禁止空 options 的 `needs_user`。

网关 `result()` 在需要人时：

```python
status="needs_user"
user_prompt=<pause(...)>
next_action="answer_user_prompt"
```

助手合同（写进 `AGENTS.md` 产品段落，不要写进 sopcontrol 投影区）：

1. 把 `user_prompt.question` 和 `options` 原样列给用户。
2. 不得增删选项，不得改 label。
3. 用户选定后，只按 `reply_contract` 再调网关，不得改用旧 CLI。

### 7.2 职位名：你举的例子怎么接

现状：`package_context` 加 `role_confirmation_required`，`materials_vnext/bundle.py` `raise ValueError("role_confirmation_required")`，engine 只回 blocker 码。

改法：

1. `PackageContextLoader.load` 在追加 `role_confirmation_required` 时，同时把 `role_title_contract.variants` 放进 `ctx.user_prompt_data`（新字段，默认 None）。
2. `MaterialsEngine.handle` 捕捉该 blocker 时，不要只回字符串。调用 `pause(kind="choose_role_title", ...)`。
3. 选项：每个 variant 的 `material` 为 `id` 和 `label`；`recommended` 给当前 `primary`（斜杠第一段）。
4. `why_it_matters`：固定文案「简历标题、求职信开头会用这一个；文件名由系统生成。」
5. `reply_hint`：`回 1 或 2，或直接说要用的职位名。`
6. `reply_contract`：

```json
{
  "action": "materials",
  "command": "python3 -m tools.workflow materials role-choose --job-id <id> --title <label>"
}
```

7. 新增网关子命令，**不要**再让助手去调 `python3 -m tools.job_materials role choose`（那是包内工具，可保留给调试）：

```bash
python3 -m tools.workflow materials role-choose --job-id C0-005 --title "Legal Assistant"
```

实现：在 `tools/workflow/__main__.py` 的 materials 分支识别 `role-choose`，内部调用现有 `tools.job_materials` 的 choose 逻辑（或把 `cmd_role` 抽成函数供两处使用）。选完后 `confirmation_needed=false`，`selection_mode=user_override`。然后材料可以继续。

`ECM/IPO` 一类复合词继续不提问，现有测试 `test_legacy_stale_confirmation_for_acronym_compound_is_repaired_by_host` 保持。

文件名超过 80 字符：**不问**。若本次渲染发生了压缩，在 `succeeded` 结果里加只读字段：

```json
"filename_note": "文件名已缩短以符合 80 字符限制；材料正文和 job_manifest 仍使用完整职位名与公司名。"
```

来源：`build_filename_stem()` 已有 `shortened` / `compression_applied`。从 renderer receipt 抄到 workflow 结果即可。

### 7.3 其它停顿都换成同一张卡

| 现有出口 | 改成 |
|---|---|
| push 预览 `status=planned` `next_action=push_confirm` | `needs_user` + `confirm_push`，选项：确认入表 / 取消；若 `selection_required`，选项就是 `review_rows` 里每一岗（id=url 或 scan key） |
| intent 预览 | `confirm_intent`：写入 / 放弃 |
| base confirm 预览（未带 `--confirm`） | `confirm_base`：激活该 lane / 再改内容 |
| preflight `next_action=ask_user` | `ask_preflight`，每个 `questions[]` 一张卡或一张卡多问，但 options 要能回传 `field_id` |
| 无运行实例 | `setup_required`，唯一选项「去跑 /setup」 |

push 选岗的 `reply_contract`：

```bash
python3 -m tools.workflow push --select <key1>,<key2>
# 用户确认后再
python3 -m tools.workflow push --confirm <proposal-id>
```

不要在停顿卡里让模型拼 rows。

### 7.4 测试

新建 `tests/test_user_prompt.py`：

- `pause()` 缺 options 抛错
- 职位歧义的 materials plan 返回 `status=needs_user`、`user_prompt.options` 长度 = variants、含 recommended
- `role-choose` 后再次 plan 不再 `needs_user`
- ECM/IPO 不出现 `choose_role_title`
- push 预览是 `needs_user` 且无 ticket secret

改 `tests/test_materials_workflow_contract.py` 的 `test_pending_role_confirmation_blocks_planning`：仍阻断进入 planning，但结果带 `user_prompt`。

## 8. 改动四：材料对外三步

### 8.1 映射，不重建引擎

内部 phase 不变：`idle → plan_ready → … → pdf_generated → format_passed → apply_ready`。

对外只暴露：

| 用户步 | 内部 | 用户说的话 |
|---|---|---|
| `check` | 冻结 bundle + 收集停顿（职位名、preflight、缺基础版、缺 JD） | 「先核对这个岗」 |
| `produce` | 能跑的 plan/draft/audit/render/pdf/format 一直跑到下一个 `needs_user` 或 `format_passed` | 「出材料」 |
| `apply` | 现有 apply adapter | 「能不能投」 |

CLI：

```bash
python3 -m tools.workflow materials --job-id C0-005
# 默认等价于 check；若无停顿，自动 produce 到下一个停顿或完成

python3 -m tools.workflow materials --job-id C0-005 --stage check
python3 -m tools.workflow materials --job-id C0-005 --stage produce
python3 -m tools.workflow apply --job-id C0-005
```

`--stage plan|draft|render|pdf_generated` 仍留给测试和调试，不写进 slash command。

### 8.2 `produce` 怎么跑

在 `MaterialsEngine.handle` 增 `stage in {"produce", "make"}`：

```text
loop:
  若有 user_prompt 级 blocker → 返回 needs_user（不进入渲染）
  若缺独立审计结果且 provider=none → 返回 needs_user
      kind 不要新造「请模型自己审」；用现有 delegation：
      question: 「内容审计需要隔离上下文。请在当前助手里开一个独立审计任务。」
      options: [{id:"launch_auditor", label:"按返回的 task packet 启动审计"}]
      这不是让用户审简历内容，是让助手走已有独立审计协议
  否则按现有顺序推进一格（plan 已有则 draft，audit 已过则 render…）
  单次 produce 最多推进到 format_passed
  任一步 blocked → 停，把内部 blockers 转停顿卡或硬失败
```

不要在 produce 里自动伪造审计通过。

无 `JOBSFLOW_AUDITOR_COMMAND` 时，桌面助手本来就要开子上下文。停顿卡把这件事说成人话，但 `reply_contract` 仍是现有 `audit_task_packet`，不是用户手填「我觉得没问题」。

### 8.3 slash command

重写 `.claude/commands/materials.md` 开头为：

```text
1. python3 -m tools.workflow materials --job-id <id>
2. 若 status=needs_user：把 user_prompt 问用户，按 reply_contract 回传
3. 再跑同一命令，直到 succeeded 或 apply
4. 禁止直接调旧 tools.job_materials 生成入口
```

删掉命令文档里给模型看的长内部 phase 列表，或移到 `docs/materials_vnext.md`。

### 8.4 测试

- produce 在 `role_confirmation_required` 时零 DOCX 副作用
- check 不写 canonical
- 审计未过 produce 不得 render
- 现有 vnext 单测保持，内部 stage 名不删

## 9. 改动五：doctor 下一动作

### 9.1 要改什么

`tools/workflow/__main__.py` 的 doctor 分支，以及可选小函数 `tools/workflow/doctor_next.py`（避免 `__main__.py` 再膨胀）。

在现有 checks 之后算一个排序过的 `next`：

```python
{
  "next": {
    "id": "confirm_base_lane_c",
    "say": "先确认 C 方向基础版，才能做合规岗材料",
    "command": "python3 -m tools.workflow base status"
  },
  "queue": [ ... 最多 3 条 ... ]
}
```

优先级（遇到第一条未完成就把它作为 `next.id`）：

2. 没有运行实例 → `/setup`
