# JobsFlow 外壳交互层改进技术手册（执行版）

版本：1.0

日期：2026-09-12

状态：供外部执行模型实施；本手册本身不代表代码已经完成。

## 0. 任务摘要

本任务只改 JobsFlow 的“外壳交互层”：统一工作区识别、统一用户停顿卡、统一对外状态、有限自动续接和 doctor 下一动作。

不得借此任务重建扫描器、评分器、材料引擎、SOP Control 状态机或 JobsDB 浏览器链。内部业务状态和 vNext 材料链必须继续由现有产品代码负责。

目标是让不同模型、不同 harness 和不同对话都看到同一套可执行交互契约：

```text
模型调用统一 gateway
        ↓
外壳返回稳定的 succeeded / needs_user / blocked / failed
        ↓
需要用户决策时返回固定选项和机器可回传字段
        ↓
模型原样展示，不自行改写、不自行猜测
```

## 1. 必须遵守的边界

### 1.1 产品线和私人线

- 只修改产品仓库 `/Users/xiezhijie/ai-job-search` 下的公共代码、测试和文档。
- `JobSearch_2026/` 是私人运行实例，禁止读取私人简历、JD、表格、Cookie、Chrome profile 或成品材料来改代码。
- 不得提交或推送 `JobSearch_2026/` 及任何运行时产物。
- 产品代码必须通过统一入口运行：

```bash
python3 -m tools.workflow <action>
```

### 1.2 SOP Control

- 不得直接编辑 `.sopcontrol/` 内的 registry、ledger、ticket 或 evidence 文件。
- 需要新增或调整规则时，使用 `sopctl` 生命周期命令。
- `AGENTS.md`、`CLAUDE.md` 的 SOP 投影必须由 `sopctl project all` 生成，禁止手工修改投影区。
- 外壳不能绕过 SOP admission、状态机、确认、审计或格式门。

### 1.3 旧链和自动投递

- 不得恢复旧材料 pipeline、旧 DOCX/PDF renderer 或直接编辑成品。
- 不得通过外壳绕过 `materials-vnext-1`。
- 不得自动提交求职申请；`apply` 只能验证材料和进入用户确认。
- 不得把“外壳更易用”理解为“可以替用户确认”。

## 2. 当前系统事实

当前产品已经具备以下内核能力：

- `WorkflowEngine` 是高层动作入口；
- `scan / push / materials / apply / intent / base / archive` 均有统一 gateway；
- 材料制作固定使用 `materials-vnext-1`；
- CV 和 Cover Letter 分别从自己的 lane 基础版出发；
- 内容审计、DOCX 渲染、PDF 转换和机械格式门按既有链路执行；
- SOP Control 已接入 workflow admission 和规则 consumer；
- Capability Ticket 已支持 CLI 传输和原始 `run_id` 恢复，但当前默认仍是显式 challenge → retry；
- 当前 `_workspace()` 不会从产品根目录静默选择私人 `JobSearch_2026/`，这是有意的隐私边界；
- 内部 `planned`、`delegation_required`、`content_audit_pending` 等状态已经被测试和 receipt 使用。

执行模型必须在这些事实上增量改造，不得假设系统是空白项目。

## 3. 目标架构

新增或整理一个外壳适配层，建议命名为：

```text
tools/workflow/interaction_shell.py
tools/workflow/user_prompt.py
```

推荐调用关系：

```text
CLI / Slash Command
        ↓
interaction_shell
  ├─ resolve_workspace()
  ├─ map_internal_result()
  ├─ build_user_prompt()
  ├─ redact_output()
  └─ next_action()
        ↓
WorkflowEngine
        ↓
SOP Control adapter
        ↓
现有业务 adapter
```

外壳只能包装结果和组织调用，不能复制业务逻辑。

## 4. 统一外部结果契约

### 4.1 外部状态

对模型和用户只暴露四类主状态：

| 状态 | 含义 |
|---|---|
| `succeeded` | 本次动作完成 |
| `needs_user` | 必须用户选择或确认 |
| `blocked` | 规则、权限、状态或输入不允许继续 |
| `failed` | 环境或执行错误 |

内部状态不删除。外壳负责把内部结果映射为外部结果。

### 4.2 统一结果结构

```json
{
  "schema_version": 1,
  "status": "needs_user",
  "action": "push",
  "operation_id": "push-...",
  "message": "需要确认后才能入表",
  "user_prompt": {
    "kind": "confirm_push",
    "question": "是否将这些岗位写入 fresh 台账？",
    "options": [
      {"id": "confirm", "label": "确认入表", "recommended": false},
      {"id": "cancel", "label": "取消", "recommended": false}
    ],
    "reply_hint": "回复“确认入表”或“取消”",
    "reply_contract": {
      "action": "push",
      "confirmation_id": "..."
    }
  },
  "next_action": "answer_user_prompt",
  "internal": {
    "phase": "planned",
    "rule_ids": ["JF-PREVIEW-001"]
  }
}
```

要求：

- `options` 不能为空；
- `recommended` 最多一个；
- `reply_contract` 由主机生成，模型不得自行拼接；
- 私人绝对路径、完整 JD、简历正文、ticket secret 不进入用户摘要；
- 内部 phase 可以保留在机器 receipt 中，但不能让模型把它当成用户指令。

## 5. 工作区解析：默认安全，不静默猜私人目录

### 5.1 解析优先级

保持以下顺序：

1. 显式 `--workspace`；
2. `JOBSEARCH_ROOT`；
3. 当前 cwd 已经是合法 runtime instance；
4. 否则返回当前 cwd，但对需要私人数据的动作进行 runtime 校验。

不得因为产品根目录下存在 `JobSearch_2026/` 就自动选择它。原因是：

- 产品根目录可能同时存在多个运行实例；
- 新模型不应因省略参数就读取个人资料；
- GitHub 新用户不一定使用 `JobSearch_2026` 这个目录名；
- 这会破坏产品线和私人线隔离。

### 5.2 一次性绑定的安全做法

如果需要降低用户每次输入 `--workspace` 的负担，可以增加本地、非版本控制的 runtime pointer，但必须由用户明确选择：

```text
产品根运行 doctor
  ↓
发现可用运行实例
  ↓
返回 needs_user / setup_required
  ↓
用户选择一次
  ↓
保存本地 pointer
```

pointer 不得写入公共源码、Git tracked 文件或 SOP registry。

### 5.3 runtime gate

以下动作需要合法 runtime：

```text
scan / push / materials / apply / intent / base / archive
```

没有合法 runtime 时返回：

```json
{
  "status": "blocked",
  "blockers": ["runtime_workspace_invalid"],
  "user_prompt": {
    "kind": "setup_required",
    "question": "尚未绑定求职运行实例。",
    "options": [
      {"id": "run_setup", "label": "运行 setup"}
    ]
  }
}
```

`doctor` 可以在产品根目录运行；`setup` 是创建 runtime 的入口；二者不能被 runtime gate 错误阻断。

### 5.4 测试要求

必须覆盖：

- 产品根存在 `JobSearch_2026/` 时不得静默选择；
- 显式 `--workspace` 优先；
- `JOBSEARCH_ROOT` 优先；
- cwd 在 runtime 内时可直接使用；
- 无 runtime 时写动作返回 `runtime_workspace_invalid`；
- 产品根和私人 runtime 的 tracker/base 状态不混读。

## 6. Capability Ticket 外壳策略

### 6.1 总原则

Capability Ticket 是 SOP Control 的授权协议，不是普通用户选项，也不是长期 token。

外壳必须：

- 保持 action、scope、input fingerprint 和 operation/run ID 不变；
- 最多自动尝试一次；
- 不把 secret 写入 stdout、普通日志、模型上下文或长期材料回执；
- 第二次仍需要 ticket 时立即停止，不得循环签发。

### 6.2 允许自动兑换的范围

默认只允许低风险 scan 在显式策略下自动完成一次 challenge → redeem：

```text
scan 无 ticket
  ↓
gateway 签发一次性 ticket
  ↓
同一个 operation_id/run_id 自动兑换一次
  ↓
继续 scan
```

必须保留原始 run ID。不能在第二次调用时随机生成新的 run ID。

### 6.3 不得自动兑换的范围

以下动作继续要求显式用户确认和显式调用：

- `push` 写入台账；
- `intent` 写入意向；
- `base` 激活基础版；
- `archive` 归档；
- `apply` 进入投递确认。

这些动作不能因为外壳希望“少一步”而自动执行。

### 6.4 调试和兼容

保留 CLI 的 ticket 参数供测试和诊断使用，但生产默认不向模型显示 secret。测试必须分别覆盖：

- 无 ticket 的第一次 challenge；
- 同一 run ID 的成功兑换；
- run ID 变化时拒绝；
- fingerprint 变化时拒绝；
- ticket 重复使用时拒绝；
- 第二次 challenge 不会无限循环。

如果自动兑换策略改变了 SOP 控制语义，必须通过 `sopctl` 更新规则/证据，不得只改 CLI。

## 7. 统一用户停顿卡

新建或集中整理 `tools/workflow/user_prompt.py`，固定 `kind` 枚举：

```text
setup_required
choose_role_title
select_jobs
confirm_push
confirm_intent
confirm_base
ask_preflight
confirm_archive
```

### 7.1 停顿卡规则

- 用户看到的 question 和 options 必须由主机生成；
- 模型只能原样展示；
- 不得自行新增、删除、改写或排序选项；
- `recommended` 只是建议，不是确认；
- 用户确认后，模型只能按 `reply_contract` 回调 gateway；
- 不能把 `delegation_required` 伪装成用户确认。

### 7.2 职位名确认

职位歧义时：

1. 使用现有 host-owned `role_title_contract` 生成 variants；
2. 对每个 materially distinct role 给一个选项；
3. `ECM/IPO` 和 `IPO/ECM` 等已定义等价复合词不提问；
4. 职位确认使用统一的 gateway 子命令，例如：

```bash
python3 -m tools.workflow materials role-choose \
  --job-id <job_id> \
  --title "<selected title>"
```

不能让模型调用旧的包内 `tools.job_materials role choose` 作为正式入口。

### 7.3 其它用户决策

至少统一以下出口：

- push 预览 → `confirm_push`；
- intent 预览 → `confirm_intent`；
- base 激活 → `confirm_base`；
- 归档预览 → `confirm_archive`；
- 薪资/到岗/工作权问题 → `ask_preflight`；
- 无 runtime → `setup_required`。

## 8. 材料外部三步映射

这是外部交互简化，不是删除内部材料状态机。

### 8.1 `check`

允许：

- 解析工作区；
- 冻结 `current_job_bundle`；
- 检查 JD、岗位名、基础版和 preflight；
- 生成 plan/task packet；
- 返回职位确认或其它停顿卡。

不允许：

- 写 canonical 内容；
- 生成 DOCX/PDF；
- 修改 fresh 台账；
- 调用旧材料入口。

### 8.2 `produce`

由主机按内部状态推进，但设置明确上限：

```text
plan → bounded transform → preflight → CV/CL audit
     → render → pdf → format
```

遇到以下任一项立即停止：

- `needs_user`；
- `delegation_required`；
- 审计未通过；
- 容量超预算；
- 输入 stale；
- 状态非法；
- vNext 自检失败。

没有独立审计 provider 时，生成已有的人工复核队列，不得伪造通过。

同一 `produce` 调用最多推进有限数量的内部阶段；重新调用必须从持久化状态恢复，不能从头重做或重复渲染已经有效的产物。

### 8.3 `apply`

只验证：

- 内容审计是否通过；
- DOCX/PDF 是否存在；
- 页数、文字层、文件名、元数据是否通过；
- 是否处于 `apply_ready`。

不得自动提交职位申请。

## 9. doctor 下一动作

doctor 必须只读，输出排序后的 `next` 和最多三个 `queue` 项。

建议优先级：

1. 运行环境缺失；
2. 没有 runtime；
3. setup/intent 尚未完成；
4. lane 基础版未激活；
5. 有已入表但尚未制作材料的岗位；
6. 有 `format_passed` 但尚未进入 apply 的岗位；
7. 否则建议执行临时 scan。

doctor 不得把某个旧 CSV 文件名作为台账唯一标准。应读取统一 ledger/sync 状态，并区分本地 ledger、CSV projection 和 Sheets projection。

示例：

```json
{
  "next": {
    "id": "confirm_base_lane_c",
    "say": "先确认 C 方向基础版，才能制作该类岗位材料",
    "command": "python3 -m tools.workflow base status"
  },
  "queue": []
}
```

## 10. SOP Control 接入要求

外壳必须调用既有 `WorkflowEngine` 和 `sopcontrol_adapter`，不能自己复制 admission 或状态迁移逻辑。

外壳改动只改变展示和编排时，可以复用现有规则；如果改变以下任一项，必须通过 `sopctl` 重新登记或更新证据：

- 哪些动作可以自动兑换 ticket；
- 哪些动作必须用户确认；
- 哪些动作允许自动续接；
- runtime 选择是否属于安全边界；
- `needs_user` 与 `delegation_required` 的正式语义。

SOP Control receipt 应继续记录内部真实结果，例如：

```text
ticket_challenge
ticket_redeemed
user_confirmation_required
delegation_required
action_completed
```

外壳不能用“用户看到 succeeded”替代控制面证据。

## 11. 实施顺序

不得一次性修改所有动作。按以下切片执行，每片单独测试、单独回退：

### Slice A：结果包装和停顿卡基础设施

范围：

- `user_prompt.py`；
- `interaction_shell.py`；
- 统一结果 schema；
- 不改变业务 adapter 的内部状态。

验收：

- 空 options 被拒绝；
- recommended 最多一个；
- 用户 prompt 可序列化；
- secret、完整 JD、私人路径不出现在外部结果。

### Slice B：安全 workspace resolver

范围：

- 保留显式 workspace 优先级；
- 接入 runtime gate；
- doctor/setup 不被错误阻断；
- 不自动选择产品根下的私人目录。

验收：

- 产品根存在私人目录时仍不静默选择；
- 无 runtime 的写动作返回 `runtime_workspace_invalid`；
- cwd 在 runtime 内时可运行。

### Slice C：外部状态映射

范围：

- 仅在 CLI/shell 层将真正用户确认转换为 `needs_user`；
- 保留内部 `planned`、`delegation_required` 等状态；
- push、intent、base、archive 统一停顿卡。

验收：

- push 未确认不会写表；
- intent 未确认不会写配置；
- base 未确认不会激活；
- delegation 不会被误呈现为用户确认。

### Slice D：materials check/produce/apply

范围：

- 新增外部 facade 或 stage mapping；
- 不删除内部 vNext phase；
- produce 设最大推进步数和幂等恢复；
- 无审计 provider 时只生成人工队列。

验收：

- check 不生成 DOCX/PDF；
- produce 遇停顿立即停；
- 容量门未通过不能 render；
- apply 不自动投递。

### Slice E：scan ticket 自动续接

范围：

- 仅针对明确允许的 scan action；
- 最多一次自动兑换；
- 保持 operation/run ID 和 fingerprint；
- push 等写操作保持显式票据和确认。

验收：

- scan 一次调用可以完成合法 challenge/redeem；
- ticket 不出 stdout；
- 错 fingerprint、过期、重复使用和第二次挑战都 fail-closed；
- push 仍然需要确认。

### Slice F：doctor next 与文档投影

范围：

- doctor 返回 next/queue；
- 更新命令文档和产品段落；
- 如需改 SOP 规则，使用 `sopctl` 后重新生成投影。

验收：

- doctor 只读；
- next 命令可执行；
- 新模型只看产品命令即可知道下一步；
- `sopctl project check`、`sopctl audit` 和 gate 通过。

## 13. 提交纪律

- 不要使用 `git add .`；只提交本次外壳改动、测试、文档和必要的 SOP 投影。
- 不得把 `JobSearch_2026/`、个人数据、Cookie、真实 run 记录或未脱敏 handoff 加入提交。

## 14. 完成定义

本手册全部完成必须同时满足：

1. 所有高层动作仍经统一 gateway；
2. 工作区不会静默猜私人实例；
3. 用户需要决定时统一返回停顿卡；
4. `planned`、`delegation_required` 和 `needs_user` 没有混淆；
5. scan 的低风险 ticket 续接最多一次，写操作仍需显式确认；
6. materials 对外可以使用 `check → produce → apply`，内部 vNext phase 不变；
7. doctor 只读且给出可执行下一步；
8. SOP Control receipt、规则、投影和测试保持一致；
9. 所有测试和 gate 通过；
10. 私人运行实例和 JobsDB 私人浏览器状态没有进入公共产品线。

最终原则：

> 外壳负责把系统说清楚，gateway 负责把动作管住，内核负责把任务做完，SOP Control 负责留下可验证证据。任何一层都不能替代另一层，也不能以“用户体验”为理由绕过安全边界。
