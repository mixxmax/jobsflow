# JobsFlow 材料制作新链重建执行方案

- 状态：设计草案，尚未进入实现
- 日期：2026-08-15
- 范围：仅替换 `/materials` 到 `/apply` 的材料制作子系统
- 不变量：检索、评分、入表、Fresh 生命周期、JobsDB 本地策略和私人运行数据不在本次重建范围内

## 1. 决策摘要

本次不继续扩展现有材料编排器，而是在产品线中建设一条新的材料引擎，验收后由统一 gateway 一次性切换。旧材料链停止承担生产职责；其中稳定、边界清楚的能力以库的形式复用，旧编排、旧状态、旧 fallback 和旧模型入口不继承。

用户看到的业务流程保持简单：

```text
选择已入表岗位
  -> 系统冻结当前岗位输入
  -> 主模型基于 CV/CL 基础版提交有限定制
  -> 系统编译完整 CV/CL 并做确定性预检
  -> 独立上下文审计 CV/CL 内容
  -> 必要时主模型定向修复并复审一次
  -> 系统按 lane 基础版生成 DOCX/PDF
  -> 机械格式验收
  -> apply-ready，等待用户决定是否投递
```

新引擎只维护四个单一真相：

1. `current_job_bundle`：本轮允许使用的全部输入。
2. `effective_transform`：基础版到最终正文的可重放增量。
3. `generation_id`：本轮 canonical、审计和外发产物的同代标识。
4. `materials_run.phase`：唯一权威状态。

## 2. 为什么选择重建，而不是继续修补

现有材料链已经出现以下结构性问题：

- 同一个业务动作分散在旧材料 CLI、workflow adapter、orchestrator、entity state 和 package validator 中。
- 职位、雇主、招聘机构、email 和文件名存在重复解析。
- 原始 transform、canonical 和 repair 不是同一个可重放事实，reset 后可能重现旧错误。
- run state、entity state 和实际产物可能分别报告不同阶段。
- 旧包、旧 DOCX/PDF、旧 email 和新 canonical 可能混代。
- 模型可绕开声明式 read scope，查看其他岗位包或旧成稿。
- 当前产品线已有部分 generation、baseline 和隔离模块，但仍嵌在旧编排器中，尚未形成闭环。

截至本方案编写时，当前工作树的材料改动与本地 JobsDB 改动混在同一分支，材料相关测试还存在收集错误。因此不得在当前工作树上直接继续堆叠实现；必须先完成第零阶段的基线隔离。

## 3. 产品范围

### 3.1 本次重建包括

- `/materials` 的输入冻结、planning、bounded tailoring、canonical 编译、内容预检、自动独立审计、定向修复、DOCX/PDF 渲染和恢复。
- `/apply` 对新材料 generation 的完整性验证和 apply-ready 判定。
- 当前岗位的职位、雇主和招聘机构统一实体契约。
- CV 与 CL 各自以当前 lane 基础版为内容母版和格式母版。
- deterministic email 生成，但 email 不进入子 Agent 审计。
- 本地台账的材料状态投影；不得自动 promote、归档或投递。
- 旧材料包的按需重建和旧生产入口的退役。

### 3.2 明确不包括

- `/scan`、两段评分、召回、JD 抓取和门户策略。
- `/push` 的入表规则、编号分配和 Fresh 排序。
- JobsDB 的本地人工验证/session 方案。
- 自主学习系统的完整建设；本次只冻结并读取已有 lessons 快照。
- 自动投递网站或替用户提交申请。
- 对用户已经确认的履历、GPA、语言和工作经历进行外部真实性调查。
- 重写所有基础版内容或所有 DOCX 模板。

## 4. 产品线、运行实例与远端边界

- 新引擎只在 tracked 产品代码中实现。
- `JobSearch_2026` 继续只是私人运行实例，存储画像、JD、岗位包、状态和产物，不拥有第二套代码或规则。
- 运行实例直接调用产品引擎，不需要复制或部署规则。
- 真实私人数据只用于最后的人工授权试跑；自动测试使用匿名 fixture。
- 本地 JobsDB 专用改动保持在既有本地分支，不进入材料重建分支，也不因材料重建而改变远端行为。
- 是否 commit、push 和发布由后续明确指令决定；本方案本身不授权推送。

## 5. 新链路总体架构

### 5.1 单一高层入口

公开命令保持不变，但全部路由到新的 `MaterialsEngine`：

```text
/materials -> python3 -m tools.workflow materials ...
/apply     -> python3 -m tools.workflow apply ...
```

模型、Slash Command 和 runtime delegate 不得直接调用内部阶段或旧 authoring CLI。内部可保留阶段命令用于测试和恢复，但外部只能通过 gateway 请求下一合法动作。

### 5.2 深模块划分

新链按责任分成以下模块，模块之间只通过版本化结构传递数据：

| 模块 | 唯一职责 |
|---|---|
| Current Job Bundle Builder | 收集、规范化并冻结本轮全部输入 |
| Entity Resolver | 唯一解析职位、雇主、publisher 和 application target |
| Baseline Compiler | 从当前 lane 的 CV/CL 母版生成版本化 blocks |
| Tailoring Compiler | 验证模型 delta，生成 effective transform 和 canonical |
| Content Preflight | 在使用子 Agent 前完成所有确定性内容门 |
| Audit Coordinator | 自动派发独立上下文、限制轮次并管理 findings |
| Generation Store | 管理 generation、reset、缓存和同代产物 |
| Renderer Gateway | 唯一生成 DOCX、PDF 和 deterministic email |
| Apply Gate | 验证内容、格式、哈希和状态，计算 apply-ready |
| Tracker Projector | 只把材料状态投影到已有本地/远端行 |

`MaterialsEngine` 只负责编排这些深模块，不重复实现它们的业务规则。

## 6. Current Job Bundle

### 6.1 内容

每次全新 planning cycle 生成不可变 bundle，至少包含：

- job ID、package binding、lane、tier；
- 完整 JD 与 JD hash；
- 当前用户画像、已确认 facts 和能力上沿的受控视图与 digest；
- assessment 和 preflight；
- 唯一 entity contract；
- CV/CL baseline digest 和版本；
- 当前规则包版本；
- 本轮 lessons snapshot digest；
- bundle schema version 与 bundle digest。

### 6.2 原则

- bundle 是本轮唯一输入权威；下游不再重新读取并合并 manifest、company research 或其他配置。
- 用户确认的基础资料被视为可使用事实，不因没有外部证据而被否决。
- 能力上沿只允许生成可迁移表述，不能升级成已经完成的直接经验。
- bundle 变化统一使 plan、transform、canonical、审计和 render generation stale。
- staging 只保存 bundle 的受控投影，不成为第二真相。

## 7. 职位、雇主和招聘机构实体契约

### 7.1 职位规则

- `KYC/CDD Officer`、`AML/KYC Analyst`、`UI/UX Designer` 等领域复合词保留为一个职位。
- `Manager / Assistant Manager` 等真正的多职位才进入 `pending_confirmation`。
- 薪资、job ID、地点和工作安排等元数据从材料职位中删除。
- 有业务含义的括号完整保留，除非用户明确选择较短标题；不得用逗号或短横线代替括号。
- `pending_confirmation` 是 planning 前硬门，不得静默选择第一个 variant。

### 7.2 publisher 规则

- publisher 与 employer 是不同实体。
- 招聘机构发布且客户未披露时，employer 为空，外发公司行使用中性表述。
- 招聘机构名称不得进入文件名、用人公司行或以雇主身份进入 CL。
- 若某招聘机构名称确实属于候选人历史经历，只能在对应经历事实中出现，不能因此成为当前用人公司。
- renderer、email、filename、audit 和 validator 只读取同一个 entity contract，不自行 fallback。

## 8. 基础版、transform 与 canonical

### 8.1 基础版原则

- CV 和 CL 是平行材料，各自从同 lane 的对应基础版出发。
- 基础版同时是格式母版、稳定事实母版和内容下限。
- 未被 transform 提及的 blocks 由 host 自动保留。
- 允许 rewrite、reorder、merge 和适度 add；不允许静默 delete。
- host-managed contact、role、recipient、company 和 subject blocks 不允许模型改写。

### 8.2 effective transform

模型只提交小型、结构化 delta。Host 负责：

- 校验 block ID、material、action 和 JD anchors；
- 合并未改动 blocks；
- 记录 original transform；
- 将 finding-scoped repair 追加为 patch；
- 重放 original + patches，生成 effective transform；
- 从 effective transform 纯函数式生成 canonical CV/CL。

删除 canonical 后重新构建，必须得到同一语义结果。reset 或模型切换不能让已修复错误复发。

### 8.3 修改幅度

- 正常定制聚焦少数最高价值 blocks。
- 较大幅度修改进入更强审计配置，但仍走同一条链。
- 等价于整份重写时 fail closed，要求重新提交 bounded delta。
- 系统不以“字数必须增加”为目标，而以不丢失基础版稳定证据和提高 JD 相关性为目标。

## 9. 较弱模型执行契约

### 9.1 任务拆分

同一条链固定拆为三个窄任务：

1. Planning：只识别 JD duties、requirements、themes、match type 和 coverage disposition。
2. Tailoring：只返回基础版 block 的 bounded delta。
3. Repair：只修改 finding 指向的 target，并携带精确 before text。

较强模型和较弱模型走完全相同的入口、schema、状态机和 renderer；系统不允许模型选择“简化旧路径”。

### 9.2 模型不负责

- 文件路径和岗位包选择；
- 职位/雇主/publisher 解析；
- 哈希、generation、状态迁移；
- canonical 的完整组装；
- DOCX/PDF/email 写入；
- apply-ready 判定；
- Tracker promote、归档或投递。

### 9.3 错误恢复

- Schema 错误返回字段级错误和唯一 response template，不产生副作用。
- Schema 修正不计入语义审计轮次；同一模型响应最多自动修正一次，仍失败则明确阻断。
- 切换模型时从当前 pending task 继续，不重做已通过阶段。
- 所有枚举、必填字段和允许动作由 host 提供；模型不能自行发明字段。
- 长手册不进入每次调用，只提供编译后的短规则和当前任务数据。

## 10. 安全护栏

### 10.1 读取边界

优先使用 tool-less stdin/API：Host 读取允许输入并直接传给模型，模型只返回 JSON，不获得仓库文件工具。

若平台只能通过 CLI 调用模型：

- cwd 限制在当前任务 staging；
- 只读 allowlist 文件；
- 只写唯一 response/result；
- 禁止父目录、其他岗位包、profile 原始目录、HOME 凭据和网络；
- 拒绝 symlink、绝对路径和越界路径；
- 实际没有 OS 隔离时只称 bound staging，不宣称 sandboxed。

### 10.2 写入边界

- 模型永远不直接写 package、DOCX、PDF、email、receipt 或状态。
- Host 先在 generation staging 中生成并验证，再原子发布。
- 所有写入使用 package containment、regular-file 和 no-symlink 检查。
- 同一 job 串行并加 package lock；不同 job 可有限并行。

### 10.3 内容边界

子 Agent前的确定性 Content Preflight 至少检查：

- entity contract 与 host-managed blocks；
- recruiter/雇主边界；
- baseline content floor；
- placeholders、内部备注和确定性残句模式；
- 用户确认数字和 profile facts；CV 与 CL 分别对共享事实校验，不互相作证；
- 主动暴露缺点，例如 `rather than <missing domain>`、`would be new`、`an area I would build`、`although I lack`、`I do not have`、`not declared in my profile`；
- coverage disposition 与正面回应一致；`intentionally_omitted` 只能留在内部；
- 角色、语言和跨材料真实矛盾。

预检失败时不创建审计任务、不增加 audit attempt、不生成 DOCX/PDF。

### 10.4 非可信输入

- JD、公司页面和网页文本一律作为数据处理，不能改变系统提示、工具权限或工作流。
- 外部文本中的指令、秘密索取、路径和脚本不进入模型控制层。
- 产品测试和日志不得复制私人姓名、联系方式、真实材料正文或完整私有 JD。

## 11. 子 Agent 审计设计

### 11.1 审计范围

子 Agent只审 CV/CL 内容：

- JD 主要职责和要求是否得到真实、积极回应；
- STAR 的 Action + Object，以及有事实支持时的 Method/Result；
- LLMO 的摘要、Core 和首条证据排序；
- CL 的 need -> evidence -> value 与差异化；
- 语法、截断、重复、角色与 recruiter 边界的轻量全局回归。

不审 email、DOCX、PDF、页数、字体、颜色、元数据、文件名、lane 或评分。

### 11.2 独立性

- 审计可以使用与主模型相同的模型，但必须是独立上下文。
- 审计只收到 current JD、最终 canonical CV/CL、tailoring delta、entity/layout contract 和短规则包。
- 不读取事实库、其他岗位、长手册、旧审计、email 或格式产物。
- 审计只写结构化结果，不修改材料。

### 11.3 轮次与争议

- 正常路径：一次完整审计。
- 有阻断 finding：主模型只提交定向 repair，然后进行一次定向复审和轻量全局回归。
- 第二次仍有阻断 finding：进入 `human_review`，不自动第三审。
- P2 永不触发自动返工。
- 主模型 dispute 不能直接放行，必须给出证据并由第二次独立审计判断。
- 同一 finding 再现立即计入第二轮，不因换措辞获得新轮次。

## 12. Generation、状态与 reset

### 12.1 标识

- `run_id`：一次完整 materials lifecycle。
- `generation_id`：一版 canonical 内容及其全部派生产物。
- renderer receipt 使用 canonical hash 和 generation ID 即可；第一版不额外引入独立 render 状态 ID。

### 12.2 唯一状态

`materials_run.phase` 是唯一真相，建议阶段为：

```text
idle
-> bundle_ready
-> planning_pending
-> tailoring_pending
-> content_preflight
-> audit_pending
-> repair_pending
-> content_passed
-> rendered
-> format_passed
-> apply_ready
```

外部 entity state 只做可重建投影，不能反向覆盖 run。

### 12.3 幂等与 reset

- 同 generation 重复合法命令返回 cached/verified，不报非法迁移。
- `reset audit`：保留 canonical，归档审计和 repair handoff。
- `reset render`：归档 DOCX、PDF、email 和格式 receipts。
- `reset draft`：归档 canonical 及全部下游产物，再从 effective transform 重放。
- `reset all`：归档整个 run，保留岗位包输入，启动新 bundle/planning cycle。
- reset 必须 preview + confirm，且不可删除不可恢复数据。

## 13. Renderer 与格式门

- renderer 继续复用 lane master 的字体、颜色、边距、样式、tab 和段落原型。
- 内容审计通过后才正式生成 DOCX。
- CV 和 CL 的 PDF 可并行转换，但必须使用固定 LibreOffice 链。
- email 由 host 根据 candidate、role 和 entity contract 固定生成，不调用模型、不进入子审计。
- 格式门只检查页数、文字层、文件名、元数据、模板样式一致性和 canonical 渲染等价。
- 允许 renderer 在预先规定的范围内调节段间距和留白，不改变字体、颜色或正文。
- 如果格式调整仍无法一页，回到主模型压缩指定内容 targets，并只进行一次定向复审；不得手工改 DOCX 后伪造审计哈希。

## 14. 可复用资源

### 14.1 直接复用

- 已入表岗位包及 package binding。
- JD store、JD depth/hash 和用户粘贴 JD 机制。
- profile facts、能力画像、assessment 和 preflight 的读取能力。
- lane CV/CL master discovery 和 DOCX 样式模板。
- LibreOffice PDF converter。
- 原子文件写入、哈希、路径 containment 和安全日志工具。
- model-neutral auditor provider 配置思想。
- 本地 TrackerLedger/SyncCoordinator 的投影能力。
- 现有匿名测试 package builder 和 PDF/DOCX fixture 思路。

### 14.2 经重构后复用

- role-title parser：修复复合 slash、薪资括号和 pending confirmation 后复用。
- publisher classifier：收敛为唯一 resolver 后复用。
- baseline block extractor：增加版本和 host-managed contract 后复用。
- canonical renderer：移除旧 manifest fallback，改为只消费新 generation 后复用。
- package validator：拆成 content preflight、format gate 和 apply gate 后复用规则。
- auditor dispatcher：改为 tool-less 优先、两轮预算和明确 provider failure 后复用。

### 14.3 不复用为生产控制层

- 旧 `tailor/pipeline` authoring 路径。
- 现有大而多分支的 materials adapter/orchestrator 作为状态权威。
- 旧 claim authorization contract 作为子审计输入。
- 重复的 company/recruiter fallback。
- 允许直接传入完整 canonical 的模型入口。
- 旧 DOCX、PDF、email 和 `.md` fallback 搜索。
- run state 与 entity state 双向推进机制。
- runtime 私人脚本拥有独立材料规则的方式。

## 15. 旧链退出与破坏策略

“彻底替代”指生产调用上的硬切换，不要求第一天删除所有可复用库代码。

### 15.1 切换前

- 新引擎在独立分支/worktree 中建设，不连接真实 runtime。
- 使用匿名 fixture 完成全部单元、契约和端到端验收。
- 旧 `/materials` 在主线继续可用，直到新引擎达到切换门槛。
- 不在一个真实岗位中混用新旧 generation。

### 15.2 切换时

- 统一 gateway 一次性路由到新引擎。
- 旧 authoring 命令返回稳定错误和新入口说明。
- 删除模型可见文档中的旧路径、旧 schema 和旧恢复方法。
- 旧 adapter 不再被任何公开命令、runtime delegate 或测试夹具调用。

### 15.3 切换后

- 保留一小段只读兼容能力，用于识别和归档旧包，不允许继续生成。
- 经过一个稳定周期后，删除无调用者的旧编排、旧状态和旧 validator 分支。
- 通过 `rg`、import graph 和 clean-clone 测试证明生产入口唯一。

## 16. 旧包迁移

- 新包直接使用新引擎。
- 旧包如果缺少可验证 bundle、baseline 和 transform provenance，标记为 `legacy_generation_unbound`。
- 旧包产物移动到可恢复的 `.history` 后，从岗位输入、共享画像和 lane 基础版重新生成。
- 不从旧 canonical、旧成稿或其他岗位反推新 transform。
- 不批量改写所有历史包；只在用户再次制作或明确迁移某个岗位时按需重建。
- 私人试跑必须另行获得明确授权，并且不得自动修改既有已投材料。

## 17. Tracker 边界

- apply-ready 后更新本地权威 ledger 的“材料状态”。
- 只投影到该 job ID 已存在的目标表/CSV 行。
- 不创建不存在的主表行，不自动 promote，不归档 Fresh，不自动投递。
- 同步失败返回 `sync_pending` 和可重放 operation，不撤销已完成材料，也不伪装同步成功。

## 18. 实施分支与第零阶段

当前工作树不适合作为直接重建基线：它同时含本地 JobsDB 和大量未收口材料改动，且材料测试存在 collection error。

开始实现前必须：

1. 只读导出当前分支、tracked diff、untracked 文件和测试结果清单。
2. 区分本地 JobsDB 改动、已验证产品改动、材料实验代码和无关文件。
3. 不使用 reset/checkout 丢弃用户工作；需要清理时先生成可恢复 snapshot。
4. 选择最后一个 clean、可测试的产品基线。
5. 创建独立 `codex/materials-vnext` 分支和 worktree。
6. 只把经过决定复用的稳定能力带入新分支，不整体复制当前半成品 orchestrator。
7. 新 worktree 不连接 `JobSearch_2026`；直到匿名 E2E 通过才允许受控试用。

## 19. 小提交执行顺序

每个提交必须保持测试可收集、已存在非材料功能不回归、且不连接私人 runtime。

1. **记录材料 vNext 契约与测试夹具**：固定公开命令、四个单一真相、匿名 G/C fixture 和无副作用 engine skeleton。
2. **实现 Current Job Bundle**：冻结输入、版本和 digest；证明其他岗位变化不会改变本 bundle。
3. **收敛 Entity Resolver**：修复复合 slash、薪资元数据、confirmation hard gate 和 recruiter 边界。
4. **实现版本化 Baseline Compiler**：CV/CL 双母版、host-managed blocks、cache version 和 content floor。
5. **实现 bounded Tailoring Compiler**：只接受 plan/delta schema，host 编译完整 canonical。
6. **实现 effective transform 重放**：original、repair patches、generation 和删除 canonical 后重建。
7. **实现 Content Preflight**：实体、内容下限、用户确认事实、缺点暴露、占位符和一致性门。
8. **实现单一 Materials Run Store**：合法阶段、revision、幂等 operation 和精确 reset。
9. **实现 Producer Dispatcher**：tool-less 优先、bound JSON、单次 schema 修正和平台无关错误。
10. **实现 Audit Coordinator**：自动独立上下文、短规则包、首审 + 一次复审、P2 非阻断。
11. **接入固定 Renderer Gateway**：同代 DOCX、并行 PDF、deterministic email 和 metadata ownership。
12. **实现 Format/Apply Gate**：同代哈希、canonical 等价、页数、文字层和 apply-ready。
13. **接入 Tracker Projector**：只更新已有行，绝不 promote/归档/投递。
14. **增加旧包识别与按需重建**：只读检测、可恢复归档和 legacy blocker。
15. **在测试分支切换公开 gateway**：禁用旧 authoring，删除模型可见旧入口。
16. **完成匿名 E2E 与 clean-clone 验收**：强/弱模型夹具、LibreOffice、sandbox、reset 和并发。
17. **清理无调用旧编排并更新文档**：通过 import/command 扫描证明生产链唯一。

如某提交需要大范围修改，必须继续拆分；不得用一个巨型提交同时修改状态、renderer、audit 和 tracker。

## 20. 测试策略

### 20.1 测试原则

- 测试外部行为和业务不变量，不锁死内部函数布局。
- 每个真实失败都转为一个最小匿名 fixture。
- 确定性代码测试不得调用真实模型、浏览器或网络。
- 模型测试使用 provider stub，明确记录调用次数、输入范围和输出 schema。
- 真实 LibreOffice、CLI sandbox 和 clean clone 作为 opt-in 集成套件。

### 20.2 必须覆盖

- `rather than bank KYC operations` 在 audit 前阻断，audit 调用次数为 0。
- `KYC/CDD Officer (HNW client) (Up to $30K)` 生成正确材料职位；真正多职位才阻断确认。
- recruiter 未披露客户时，文件名、CL、email 均不出现 recruiter 作为雇主。
- 用户确认 GPA、工作经历和数字可直接使用；模型不得把能力上沿升级成直接经验。
- baseline parser 版本变化自动重建。
- 未修改基础 blocks 全部保留；CV 和 CL 分别以各自母版为依据。
- original + 多个 repair patches 可重放；reset 后旧错误不复发。
- 模型切换后从 pending step 恢复，不读取其他岗位。
- 首审通过只调用一次 auditor；需要修复时总计两次；第二次仍失败进入 human review。
- P2 不触发 repair 或第三审。
- producer/auditor 无法读取父目录、其他 job、profile 原始目录或网络。
- 内容通过前没有正式 DOCX/PDF；渲染后样式来自正确 lane master。
- DOCX/PDF/email/receipts 属于同一 generation，跨代混用 fail closed。
- reset 四个 scope 精确归档且可恢复。
- apply-ready 只更新已有 tracker projection，promote 调用次数为 0。
- clean clone 可完成 synthetic `/setup -> push fixture -> materials -> apply`。

### 20.3 较弱模型验收

使用固定、匿名任务包测试：

- 正确但简短的 delta；
- 缺字段、错枚举、错误 block ID；
- 试图提交完整 CV/CL；
- 试图删掉基础版内容；
- 试图暴露缺点；
- 试图读取其他岗位作为范例；
- 切换模型后继续 repair；
- 子审计给出缺 target 或越权检查 PDF。

验收不是比较模型文风，而是验证弱模型的错误被 host 收窄为可理解、可恢复且无副作用的结构化结果。

## 21. 性能与资源预算

正常单岗目标：

- 主模型：planning 1 次、tailoring 1 次；
- 子 Agent：完整审计 1 次；
- 无额外模型调用用于哈希、格式、email、文件名或状态；
- 有真实 P0/P1 时：主模型 repair 1 次、子 Agent复审 1 次；
- 同一岗位模型调用严格串行；多个岗位最多三个并行；
- 相同 bundle + effective transform + rules 的通过结果可以缓存复用；
- 每阶段记录 wall time、模型调用数、token、cache hit、reset reason 和失败码。

建议验收目标：正常单岗 5–10 分钟内完成；本地代码和渲染阶段总耗时远小于模型调用。若超时，必须能从事件记录定位到具体阶段，不能只显示“处理中”。

## 22. 切换门槛与回滚

### 22.1 切换门槛

- 新引擎全部 focused tests 通过。
- 全仓测试可收集且通过；浏览器类明确标为 opt-in。
- security guards 和 public source checks 通过。
- clean clone synthetic E2E 通过。
- 两个匿名真实失败 fixture 通过。
- 至少一个较弱模型和一个较强模型使用同一入口完成合成材料。
- 旧 authoring 入口扫描为零生产调用者。
- 不读取或改写私人 runtime。

### 22.2 回滚

- 切换提交保持可逆，不删除旧包和私人产物。
- 切换失败时回滚 gateway 路由，不逆向改写已产生的新 generation。
- 新 generation 带版本标记，旧引擎不得消费。
- 回滚只用于软件故障，不允许以回滚为理由重新启用模型自行选择旧入口。

## 23. 完成定义

只有同时满足以下条件，才能宣布材料新链完成：

- 用户只需点名已入表 job ID；模型不需要理解文件夹、哈希或内部状态。
- 任意受支持模型走同一入口、相同 schema、相同 renderer。
- 当前岗位之外的材料不能成为隐式输入。
- 基础版稳定内容不会静默减少。
- 主动暴露缺点、错误职位和 recruiter 泄漏在子审计前被阻断。
- 子 Agent只审 CV/CL，正常一次、有修复最多两次。
- reset、模型切换和中断恢复不重播旧错误、不混用旧产物。
- DOCX/PDF 的样式、文件名、元数据和页数由 host 统一控制。
- apply-ready 是代码计算结果，不是模型声明。
- 旧生产链已失去所有公开和 runtime 调用入口。
- 检索、评分、Fresh、JobsDB 本地策略和私人数据边界没有被改变。

## 24. 待实现前确认的决策

本方案建议默认采用以下决定；实现前只需确认是否接受：

- 旧材料包按需重建，不做永久双向兼容。
- audit 自动轮次上限为 2，而不是 3。
- schema 修正最多自动一次，不计入 audit 轮次。
- 第一版只保留 run ID 和 generation ID，不增加独立 render ID。
- 当前工作树的半成品材料实现不整体继承，只复用经测试证明稳定的底层能力。
- Tracker 只做状态投影，绝不触发 promote、归档或自动投递。
- 新引擎先在独立 worktree 用匿名 fixture 建设，验收前不接真实求职实例。
