## 1. 必须修

### R1　全量测试恢复全绿（当前 7 个失败）

**A. 5 个 portal 测试被新的 conftest 默认值弄坏了**

- `tests/test_portal_jd_recovery.py` 中的：
  - `test_recovered_cdp_session_is_reused_for_following_jobsdb_details`
  - `test_two_pass_circuit_stops_third_url_and_cache_still_wins`
  - `test_private_two_pass_hands_first_challenge_to_one_shot_recovery`
  - `test_two_pass_counts_retry_attempts_as_real_navigations`
  - `test_jobsdb_policy_stop_precedes_legacy_failure_cache`
- 原因：`tests/conftest.py` 现在默认设置 `PORTAL_JD_BROWSER=0`，而这几个测试需要走浏览器分支（它们内部已经打了桩）。这 5 个测试在 CI 上同样会失败。
- 修法：
  1. 在这几个测试里（或给该文件加一个局部 fixture）显式 `monkeypatch.setenv("PORTAL_JD_BROWSER", "1")`。
  2. **逐个确认**它们对 CDP 附接、`_launch_user_chrome_with_debug_port`、本地端口探测都打了桩。任何一个没打桩的，都先补桩，再开启浏览器分支。
  3. 在 `tests/conftest.py` 加一个 autouse 的"绊线"：把 `JobsdbCdpBatchSession._launch_user_chrome_with_debug_port` 和对 `127.0.0.1` 调试端口的实际连接替换成直接抛 `AssertionError("test reached real Chrome")`。需要这些调用的测试自己打桩覆盖它。这样今后任何测试误触真实浏览器都会立刻失败，而不是悄悄连上。
- **不得**用 skip 或删除这 5 个测试的方式转绿。

**B. 2 个 batch 测试的替身函数签名过期**

- `tests/test_materials_canonical_pipeline.py` 中的 `test_batch_clamps_parallelism_and_isolates_job_failures` 和 `test_batch_prepare_uses_gateway_and_writes_compact_context`。
- 原因：`materials_batch._one` 新增了关键字参数 `dry_run`，而测试里的 `fake_one(_workspace, job_id, action, engine)` 不接受它，每个 worker 都抛 TypeError。
- 修法：替身签名改为 `fake_one(_workspace, job_id, action, engine, *, dry_run=False)`。**不要**改断言。

### R2　JobsDB 导航 URL 必须严格校验（白名单仍可绕过）

**现状**：`tools/job_urls.py` 的 `is_jobsdb_url` 会放行下面这些地址：

- `https://evil.test\@hk.jobsdb.com/...`：Python 把主机解析成 jobsdb，Chrome 会把 `\` 当作 `/`，实际打开的是 `evil.test`；
- `javascript://hk.jobsdb.com/...`、`ftp://…`、`http://…`；
- 非标准端口 `:8443`；
- `user:pw@` 形式。

另外，`normalize_job_url` 只会重写带 `/job/<数字>` 的地址，其余地址原样保留，最终可能被交给 `page.goto`（`portal_jd_browser.py` 约 869、2112 行）。CLAUDE.md 里"只接受真实 `*.jobsdb.com` 主机"的说法目前不成立。

**修法**

1. `is_jobsdb_url` 保留，只用于**分类**；**导航**另写一个函数。在 `tools/job_urls.py` 新增 `safe_jobsdb_job_url(url) -> str | None`，满足以下全部条件才返回规范 URL，否则返回 `None`：
   - 原始字符串不含 `\`、空白、控制字符，也不含 `%` 编码的控制字符；
   - scheme 恰好是 `https`；
   - 没有 userinfo（`parsed.username is None`，且 netloc 中没有 `@`）；
   - 端口为空或 443；
   - `host_matches(host, "jobsdb.com")`；
   - 路径能按现有正则提取出岗位编号 `jobsdb\.com(?:/[^?\s]*)?/job/(\d+)`。
   - 返回值**按编号重建**：`https://<规范化主机>/job/<编号>`，不透传原始路径和查询串。
2. 所有会导致浏览器导航的入口都改用它，拿到 `None` 就返回 blocker `jd_fetch_url_not_allowed`：
   - `adapters/intake.py` 的 `_maybe_fetch_missing_jds`；
   - `tools/workflow/jd_fetch.py` 的 `fetch_full_jds`；
   - `tools/workflow/materials_prepare.py` 的 `--fetch` 路径。
3. 纵深防御：在 `portal_jd_browser.py` 的 JobsDB 详情导航处（调用 `page.goto` 之前）再校验一次，不通过就拒绝导航并返回结构化失败。**只加校验，不改动附接逻辑。**
4. 测试（放进 `tests/test_job_url_host_whitelist.py`）：
   - 上面列出的每一种绕过形式都返回 `None`；
   - 正常的 `https://hk.jobsdb.com/job/123`、大写主机、末尾带点的主机都能通过，并规范化为 `https://hk.jobsdb.com/job/123`；
   - intake 收到绕过形式的 URL 时，抓取函数**不被调用**（用桩计数断言）。
5. 把 CLAUDE.md 和 AGENTS.md 中相关表述改为与实现一致，例如"仅 https、默认端口、`*.jobsdb.com`，并按岗位编号重建 URL"。

### R3　repost 提示实际永远不会显示（返工新引入）

**现状**：为了不给 Google Sheet 加列，`possible_repost_of` 被从 `PASS_EXTRA` 删掉了。但评分 CSV 的写入函数 `two_pass_score.write_csv`（约 1793-1800 行）只写 `SHEET_HEADERS + PASS_EXTRA` 里的列，这个字段在写入时就被丢弃了。push 从这份 CSV 读数据（`adapters/push.py` 约 245-259 行），所以 `push.py` 约 639-654 行的预览提示永远不会触发。

**修法**

1. 复用提交 ec64a15（"keep scorer bookkeeping columns out of tracker projections"）已有的机制：把 `possible_repost_of` 登记为"**写入评分产物、但不进入 tracker 投影**"的列。先找到 ec64a15 用的是哪个列表或函数，沿用同一套，**不要**另造一套过滤。
2. 同步修正 `careerops_quickscore.py` 约 1117 行过时的列数注释。
3. 端到端测试：用合成夹具跑 scan → 评分 CSV 中有 `possible_repost_of` 列 → push 预览中出现 repost 提示 → gsheet 投影和主表的表头与改动前**逐字一致**。

### R4　骨架包要明确引导用户先运行 prepare（主目标"能做出材料"）

**现状**：自动 prepare 的触发条件是 blocker ⊆ {`missing_full_jd`, `assessment_missing_or_stale`, `preflight_missing`}（`materials_prepare.py` 约 36-51 行）。但真实骨架包总会另外带上 `company_research_required` 或 `entity_contract_incomplete`（`package_context.py` 约 353、357 行），所以自动 prepare 从不触发，plan、produce 的输出里也没有任何提示。另外，`--jd-file` 有两种情况会被静默忽略。

**修法**

1. 触发条件从"子集"改为"**有交集**"：只要 blocker 里含三项准备类 blocker 中的任意一项，就先执行 prepare（它是确定性且幂等的），然后继续 plan，由 plan 照常报告剩下的 blocker。触发位置限于 idle、inputs_frozen 阶段，dry-run 时不触发（`adapters/materials.py` 约 84 行在 dry-run 下仍会调用 `PackageContextLoader.load`，这里一并改掉）。
2. 凡是输出中带有这三项 blocker 之一的材料阶段，都要附上 `next_action`，内容为可以直接复制执行的命令：`python3 -m tools.workflow materials prepare --job-id <ID> [--jd-file F | --fetch]`。
3. `--jd-file` 的处理：
   - 文件不存在或读不了 → blocker `jd_file_unreadable`；
   - 已有 `jd_full.md`、传入了 `--jd-file`、内容不同、又没带 `--refresh` → blocker `jd_file_conflicts_existing_jd`，`next_action` 提示加上 `--refresh`；
   - 以上情况都不得静默改用缓存。
4. 测试：
   - 带有 `company_research_required` 的骨架包执行 produce 时会先跑 prepare；
   - 缺 JD 时 plan 的输出带有 prepare 命令；
   - 以上两种 `--jd-file` 情况分别给出对应 blocker，且零写入。

## 4. 最终处理结果（2026-09-26）

R1–R4 已由执行方完成，并经独立复核通过。随后又直接修了以下各项。

**质检发现的两个缺口**

- **测试绊线**（`tests/conftest.py`）：原来只拦截启动 Chrome 和端口探测，现在扩展为 6 个接缝：启动 Chrome 设置页、端口探测、本机调试端口的 HTTP 请求和 socket 连接、启动 Chrome 进程、通过真实 Playwright 对象的 CDP 附接。每次命中都会记录下来，测试结束时统一判失败，所以产品代码里宽泛的 `except Exception` 吞不掉它。自测见 `tests/test_chrome_tripwire.py`。
- **`materials check` 没有 prepare 提示**：vNext 会把 blocker 拼成一整串 `context_blockers:a,b` 返回，原来的匹配认不出来。新增 `expand_blockers` / `has_prepare_blocker` 统一拆分这种串，四处调用方都改用它。

**原 §3 中已修的项**

- repair：`finding_id` 在没有未关闭审计发现时也会被拒绝；空集合与 `None`（只用于重放历史补丁）现在区分处理。
- 票据接力的范围开关由环境变量 `JOBSFLOW_HOST_TICKET_RELAY` 改为进程内 `contextvars`：shell 无法预先设置，子进程也继承不到。批量任务通过 `copy_context()` 把范围带进工作线程。接力放弃使用的票据会同时清掉它的 0600 密钥文件。
- intake：只有在"一个都没抓到"（附接失败，或所有地址都为空、都被拒）时才整单拦下；部分成功时保留已抓到的 JD，出错原因作为 `jd_fetch_errors` 警告附在预览结果里。删除了执行不到的 `except ValueError` 分支。
- 对账：第三个比对分支原本永远不会执行，现改为真实比对——包里记录的岗位链接不在账本中同一编号下时，报告 `ledger_url`。报告仍只输出编号和相对路径。
- doctor：按配置的端口比对 DevToolsActivePort，并显示实际生效的附接等待时间（`connect_timeout_seconds`）。
- DevToolsActivePort 测试：删掉永远不会触发的"非本地"断言，改为覆盖真实会发生的 `path_rejected`。
- 旧版 push 的 `select_rows_for_retention`：`pass1_low_priority` 行不再被改标为 `provisional_needs_jd`，也不再被选中。
- 评分产物 `SCORED_ARTIFACT_SCHEMA_VERSION` 升为 4，旧产物不会再被复用。
- dry-run 下的 batch：不写上下文文件，不生成人工复核队列，也不加载任何岗位包。
- import 守卫测试：能识别属性调用和别名导入；`enrich.py` 只允许由已退役的 CLI 引用。
- README_EN、README、AGENTS 补齐环境变量说明，以及"只按岗位编号重建 https 地址"的导航规则。
